# 트랜스폼 시스템 설계

**작성 2026-08-26.** 이 문서는 현재 트랜스폼의 실측 상태, 왜 "존재만 하고 조작이 안 되는지"의
근본 원인, 그리고 개선 설계를 담습니다. **코드로 넘어가기 전 검토용**입니다.

렌더링과의 결합은 얕습니다. 렌더러는 액터의 월드 행렬 하나만 소비하므로
(`Renderer_render.cpp:241`), 이 작업은 진행 중인 다른 렌더링 조사와 병행할 수 있습니다.

---

## 1. 요약

트랜스폼의 **자료 구조는 멀쩡합니다.** TRS 행렬, 부모-자식 계층, 더티 플래그 캐싱까지
이미 있습니다. 문제는 **에디터의 편집이 화면에 반영되지 않는다**는 것이고, 원인은 하나입니다.

> **렌더러는 캐시된 월드 행렬을 읽는데, 에디터의 세 편집 경로가 전부 캐시를 무효화하지 않고
> 원본 필드를 직접 씁니다.** 그래서 첫 프레임 이후 화면이 얼어붙습니다.

이것이 "이동·회전·크기 조정이 안 된다"의 단일 원인입니다. 셋이 따로 고장 난 것이 아니라
셋 다 같은 캐시를 거치기 때문에 함께 죽습니다.

부수적으로, **회전·크기 기즈모가 아예 없고**(이동 전용), 툴바의 `Q/W/E/R` 모드 전환과
`World/Local` 공간 토글이 **기즈모에 전달되지 않아 죽어 있습니다.**

## 2. 실측한 현재 상태

### 2-1. 있는 것 (자료 구조)

| 월드 행렬 캐시 | `Actor.cpp:4-11` | 존재하나 **이것이 버그의 원인** (2-3 참조) |
| 디테일 패널 수치 편집 | `EditorApp.cpp:712-726` | 위치/회전(오일러)/크기 세 줄 전부 있음 |

### 2-2. `markDirty()`를 부르는 곳 — 단 두 군데 (실측)

```
DefaultGameModule.cpp:33-34,108   씬 생성 시 1회 (setPosition/setScale)
PhysicsSystem.cpp:268-269         Play 중 Jolt 결과 되쓰기 (setPosition/setRotation)
```

`markDirty()`는 `setPosition`/`setRotation`/`setScale` 안에서만 호출됩니다
(`Actor.hpp:19-21`). 그런데 **에디터는 이 세터를 한 번도 쓰지 않습니다.**

### 2-3. 근본 원인 — 캐시 우회 (DEF-49)

```cpp
// Actor.cpp:4-11 — 렌더러가 읽는 값
glm::mat4 Actor::worldMatrix() const {
    if (worldDirty_) {                       // 이 플래그가 false 로 굳으면
        cachedWorld_ = ... transform.matrix();
        worldDirty_ = false;
    }
    return cachedWorld_;                      // 낡은 값을 계속 반환
}
```

편집 세 경로가 전부 `worldDirty_`를 건드리지 않습니다.

| 경로 | 코드 | 문제 |
|---|---|---|
| 디테일 패널 | `EditorApp.cpp:712` `sel->transform.position.x = v;` | 필드 직접 쓰기 |
| 기즈모 드래그 | `EditorGizmo.cpp:135` `selected->transform.position += ...` | 필드 직접 쓰기 |
| undo/redo | `EditorCommands.hpp:11-12` `actor->transform = before;` | 필드 직접 쓰기 |

렌더러는 `Renderer_render.cpp:241`에서 `mc->owner->worldMatrix()`를 읽습니다. 즉
**편집은 원본 `transform`을 바꾸지만 렌더러가 보는 `cachedWorld_`는 그대로**입니다.

첫 프레임에는 `worldDirty_`가 초깃값 `true`라 한 번 계산되므로 물체가 스폰 위치에
나타나기는 합니다. 그 뒤로는 무엇을 편집해도 화면이 반응하지 않습니다. 이것이
"존재만 하는 느낌"의 정체입니다.

> 이 프로젝트에 반복된 결함 유형입니다. 같은 값을 두 곳(원본 `transform`과 캐시
> `cachedWorld_`)이 서로 다르게 들고 있고, 쓰는 쪽과 읽는 쪽이 어긋납니다. DEF-24,
> DEF-25, DEF-36 과 같은 계열입니다.

### 2-4. 왜 이 버그가 "설계" 문제인가

세터가 있는데 안 썼다는 것은 표면적 원인입니다. **근본 원인은 `Transform transform;`이
public 필드라 누구든 세터를 우회해 직접 쓸 수 있고, 그것을 타입이 막지 못한다**는 점입니다.
"쓰면 반드시 더티" 라는 불변식이 **규약일 뿐 강제되지 않습니다.** 한 곳을 고쳐도 다음에
새 편집 경로를 추가하는 사람이 또 잊습니다. 설계로 풀어야 하는 이유입니다.

## 4. 설계 원칙

- **P1. 불변식을 타입이 강제합니다.** "로컬 트랜스폼을 바꾸면 파생된 월드 행렬이 무효화된다"를
  규약이 아니라 컴파일러가 보장하게 합니다. 원본 필드를 직접 쓰는 경로를 없앱니다.
- **P2. 로컬이 단일 진리 원천입니다.** 월드 행렬·월드 위치·월드 회전은 전부 로컬에서 유도합니다.
  월드 값을 따로 저장해 동기화하지 않습니다 (그것이 DEF-49 를 만든 구조입니다).
- **P3. 계층을 정확히 다룹니다.** 편집은 사용자가 보는 공간(월드 또는 로컬)에서 일어나고,
  저장은 언제나 로컬입니다. 둘 사이 변환을 한 곳에서만 합니다.
- **P4. 죽은 UI 를 되살립니다.** 이미 있는 Q/W/E/R 와 World/Local 을 기즈모에 연결합니다.

## 5. 제안 설계

### 5-1. DEF-49 — 캐시 전략 (핵심 결정 D1)

세 가지 안입니다. 아래 11절에서 선택합니다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **가 (권고)** 캐시 제거 | `worldMatrix()`가 매 호출 `parent->worldMatrix() * transform.matrix()`를 즉시 계산 | 무효화할 상태가 없어 **stale 이 원리적으로 불가능.** 가장 단순 | 부모 체인을 매 호출 순회. 얕은 계층에선 무시할 비용 |
| 나 | 세대 스탬프 | 로컬 변경 시 `localGen++`, 읽을 때 `(내 localGen, 부모 worldGen)`이 캐시와 다르면 재계산 | O(1) 편집, 성숙한 엔진의 방식 | 코드가 늘고, 여전히 "쓰면 스탬프" 를 강제해야 함 (필드 private 필요) |
| 다 | 현행 유지 + 세터 강제 | 필드를 private 로 하고 모든 쓰기를 세터로 | 변경 최소 | `markDirty`가 O(자손) 재귀. 새 경로에서 또 잊을 여지 |

**권고는 가입니다.** 현재 씬은 액터 수십 개, 계층 깊이 1~2 이고, 렌더러가 액터당 월드 행렬을
프레임당 한 번 읽습니다(`Renderer_render.cpp:241`). 즉 순회 비용이 사실상 0 입니다.
**stale 을 고치는 것이 아니라 stale 이 불가능한 구조로 바꾸는 것**이 P1·P2 에 부합합니다.
계층이 수천 개로 커지고 프로파일러가 부모 체인 순회를 지목하면 그때 **나**로 올립니다.
`worldMatrix()` 시그니처는 그대로라 소급이 쉽습니다.

세 안 모두 **원본 필드를 직접 쓰는 경로를 없애야** 합니다. `Transform`의 세 필드를
private 로 돌리고 다음 API 만 노출합니다.

```cpp
// Transform.hpp (개정안)
class Transform {
public:
    const glm::vec3& position() const { return position_; }
    const glm::quat& rotation() const { return rotation_; }
    const glm::vec3& scale()    const { return scale_;    }

    void setPosition(const glm::vec3& p) { position_ = p; }
    void setRotation(const glm::quat& r) { rotation_ = r; }
    void setScale   (const glm::vec3& s) { scale_    = s; }

    // 편의 변이 (누적)
    void translate(const glm::vec3& d)   { position_ += d; }
    void rotate   (const glm::quat& dq)  { rotation_  = dq * rotation_; }

    glm::mat4 matrix() const;            // T*R*S (변경 없음)

private:
    glm::vec3 position_ {0.f};
    glm::quat rotation_ {1.f, 0.f, 0.f, 0.f};
    glm::vec3 scale_    {1.f};
};
```

**핵심은 Actor 가 이 Transform 을 감싸서, 로컬을 바꾸는 유일한 통로가 더티(또는 캐시 무효화)를
함께 하도록 만드는 것**입니다. 안 **가**를 택하면 캐시가 없으니 더티조차 필요 없고, Actor 는
`transform_` 접근을 세터로만 열어 두면 됩니다.

```cpp
// Actor.hpp (개정안, 안 가 기준)
const Transform& transform() const { return transform_; }
void setLocalPosition(const glm::vec3& p) { transform_.setPosition(p); }
void setLocalRotation(const glm::quat& r) { transform_.setRotation(r); }
void setLocalScale   (const glm::vec3& s) { transform_.setScale(s);    }
// 편집기·물리·직렬화는 전부 이 세터만 씁니다. public 필드가 없어 우회가 불가능합니다.
```

### 5-2. 월드 공간 접근자 (DEF-52, DEF-53)

지금은 `worldPosition()`만 있고 월드 회전·스케일이 없어, 기즈모와 물리가 로컬 값을 잘못
씁니다. 월드 TRS 를 유도하는 접근자를 추가합니다.

```cpp
glm::vec3 worldPosition() const;     // 이미 있음: worldMatrix()[3]
glm::quat worldRotation() const;     // 신규: 부모 월드 회전 * 로컬 회전
glm::vec3 worldScale()    const;     // 신규: 부모 월드 스케일 * 로컬 스케일 (근사)
```

- **물리(DEF-53)**: `PhysicsSystem`이 바디를 만들 때 `transform.rotation`(로컬) 대신
  `worldRotation()`을, 위치는 `worldPosition()`을 쓰게 합니다. 부모가 없으면 로컬=월드라
  현재 동작이 그대로 유지되고, 부모가 생기면 자동으로 올바릅니다.
- **비균등 스케일 주의**: 부모가 비균등 스케일 + 자식 회전이면 월드 스케일이 순수 스케일로
  분해되지 않습니다(shear 발생). 이 경우 `worldScale()`은 근사이며 경고할 수 있습니다.
  절차 도형 규약(Capsule/Torus 는 균등 스케일만)과 같은 선상의 제약입니다.

### 5-3. 기즈모 — 모드와 공간 배선 (DEF-50, DEF-51)

`gizmo_.tick(...)`과 `gizmo_.handleDrag(...)`에 **`gizmoMode_`와 `worldSpace_`를 넘깁니다.**
기즈모는 모드에 따라 다른 핸들을 그리고 다른 드래그를 합니다.

| 모드 | 키 | 핸들 | 드래그 동작 |
|---|---|---|---|
| Select | Q(0) | 없음 (와이어 박스만) | 없음 |
| Translate | W(1) | 축 3개 + 평면 3개(선택) | 축/평면 구속 이동 |
| Rotate | E(2) | 축별 원호 3개 | 축 중심 각도 회전 |
| Scale | R(3) | 축 끝 핸들 + 중앙(균등) | 축별/균등 스케일 |

**공간(World/Local)**: `worldSpace_`가 true 면 핸들 축이 월드 축(`kAxes`)이고, false 면
액터의 `worldRotation()`으로 회전된 로컬 축입니다. 지금은 항상 월드 축이라 회전된 물체를
로컬로 밀 수 없습니다.

**계층 정확성(DEF-52)**: 드래그가 만든 **월드 공간 이동/회전을 부모 공간으로 변환한 뒤**
로컬 트랜스폼에 적용합니다. 부모가 없으면 항등 변환이라 현재 동작과 같습니다.

```
worldDelta  →  parentWorldMatrix^-1 로 변환  →  로컬 트랜스폼에 적용  →  setLocal*()
```

**바운드 반영(DEF-54)**: 와이어 박스를 고정 ±0.55 대신 메시 AABB × 스케일로 그립니다.
`MeshHandle`에 이미 `aabbMin/aabbMax`가 있습니다(`MeshHandle.hpp`).

### 5-4. 회전 편집 표현 (변경 없음)

저장은 쿼터니언, 패널 편집은 오일러(도) 유지가 표준이고 현재 구조가 이미 그렇습니다
(`cachedEuler_`, `syncEulerCache`). `syncEulerCache`가 매 틱이 아니라 **선택 변경·undo·redo
시점에만** 호출되므로(`EditorApp.cpp:213, 1115, 1121`) 편집 도중 값을 덮어쓰지 않습니다.
이 부분은 손대지 않습니다. 다만 세터를 `setLocalRotation`으로 바꾸는 것만 반영합니다.

---

## 6. 무엇을 바꾸지 않는가

- **TRS 순서, 쿼터니언 저장, 부모-자식 자료 구조**는 그대로 둡니다. 멀쩡합니다.
- **직렬화 포맷**은 바뀌지 않습니다. 로컬 position/rotation/scale 을 그대로 저장합니다.
- **렌더러**는 `worldMatrix()` 한 줄만 소비하므로 시그니처가 유지되면 변경이 없습니다.

## 7. 검증 계획

각 항목이 독립적으로 관찰 가능해야 합니다.

| # | 확인 | 통과 기준 |
|---|---|---|
| T1 | 디테일 패널 편집 | Position X 를 바꾸면 물체가 **즉시** 그 방향으로 이동 |
| T2 | 회전 편집 | Rotation Y 를 바꾸면 물체가 회전 |
| T3 | 크기 편집 | Scale 을 바꾸면 물체 크기 변화 + (물리 있으면) 콜라이더도 따라옴(DEF-41과 연계) |
| T4 | 이동 기즈모 | 축을 드래그해 이동. undo 로 복원 |
| T5 | 회전 기즈모 | E 로 전환 후 원호 드래그로 회전 |
| T6 | 크기 기즈모 | R 로 전환 후 핸들 드래그로 스케일 |
| T7 | World/Local | 회전된 물체에서 Local 이 로컬 축으로, World 가 월드 축으로 민다 |
| T8 | 계층 | 부모를 이동하면 자식이 따라오고, 자식만 편집하면 부모는 그대로 |
| T9 | 물리 정합 | 회전한 부모의 자식에 콜라이더가 시각적 위치와 겹침(DEF-53) |

**T1~T3 은 DEF-49 하나만 고쳐도 통과합니다.** 즉 "가장 큰 불만"은 캐시 수정 한 건으로 풀립니다.

## 8. 구현 순서

되돌리기 어려운 순서이자, 앞 단계가 뒤 단계의 검증 수단을 만드는 순서입니다.

1. **DEF-49 캐시 전략(D1 결정 반영).** `Transform` 필드 private 화 + Actor 세터 통로.
   모든 쓰기 경로(패널·기즈모·undo·물리·직렬화)를 세터로 교체. **여기서 T1~T3 통과.**
2. **월드 접근자.** `worldRotation()`/`worldScale()` 추가. 물리를 월드 값으로 전환(DEF-53).
3. **기즈모 배선.** `gizmoMode_`·`worldSpace_` 전달. 계층 변환(DEF-52). 바운드 박스(DEF-54).
4. **회전 기즈모(DEF-50 전반).** 원호 핸들 + 각도 드래그.
5. **크기 기즈모(DEF-50 후반).** 핸들 + 균등/축별 스케일.
6. **World/Local 로컬 축(DEF-51).** 로컬 공간 핸들.

1 단계만으로 사용자가 겪는 핵심 불편(수치 편집이 안 먹힘)이 사라집니다. 2~6 은 직접 조작
품질을 올리는 증분입니다.

### D2. 이번 작업 범위

권고는 B 입니다. A 는 핵심 불편은 풀지만 회전·크기 기즈모는 여전히 없고, C 는 원호/핸들

## 11. 회전·크기 기즈모 구현 (2026-08-26 · 4~5단계, DEF-50 완료)

이동 기즈모에 이어 회전 기즈모와 크기 기즈모를 추가했습니다. 이로써 `gizmoMode_`(Q/W/E/R)의
네 상태가 전부 동작하고, DEF-50 이 완전히 해결되었습니다.

| 모드 | 키 | 핸들 | 조작 |
|---|---|---|---|
| Select | Q | 바운드 박스만 | 없음 |
| Move | W | 축 3개 + 끝 십자 | 축 구속 이동 (부모 공간 변환 포함) |
| Rotate | E | 축별 원호 3개 | 광선-평면 교차로 각도를 구해 회전 |
| Scale | R | 축 끝 상자 3개 + 중앙 | 축별 스케일 + 중앙 균등 스케일 |

### 회전 드래그의 수학

기존 이동 기즈모는 마우스 이동량을 축의 화면 투영에 사영했는데, 회전은 각도가 필요하므로
다른 방법을 씁니다. 마우스 화면 좌표를 월드 광선으로 역변환하고(`mouseRay`, `projectScreen`의
정확한 역변환), 그 광선을 회전 평면(축에 수직, 액터 중심을 지나는 평면)과 교차시켜 교점을
구합니다. 교점을 평면 기저 `(u, v)`에 사영한 뒤 `atan2`로 각도를 얻습니다.

프레임 사이의 각도 증분을 `(-π, π]`로 감아서 누적하므로, 한 번의 드래그로 180도를 넘겨도
값이 급격히 뒤집히지 않습니다.

적용은 월드 축 회전 하나로 통일했습니다. 로컬 축 회전도 항등식
`angleAxis(a, R·e)·R == R·angleAxis(a, e)` 덕분에 같은 경로로 정확히 처리됩니다.
부모가 있으면 `inverse(부모 월드 회전) · dq · 부모 월드 회전 · 스냅 로컬 회전`으로 변환합니다.

### 크기 드래그

스케일은 언제나 로컬입니다(월드 공간 스케일 기즈모는 비균등에서 의미가 없습니다).
핸들은 로컬 축 방향으로 그리고, 조작 결과는 로컬 `scale` 성분에 곱합니다. 축별 핸들은
마우스 이동량을 축의 화면 투영에 사영해 배율을 구하고, 중앙 핸들은 세로 드래그로 세 성분에
같은 배율을 곱합니다. 배율의 하한을 0.05로 두어 음수나 0이 되지 않게 막았습니다.

### 남은 것

- **World/Local 로컬 축(DEF-51)**: 이동·회전은 `worldSpace_`를 반영합니다. 크기는 설계상
  언제나 로컬이므로 이 토글의 영향을 받지 않습니다.
- **화면 확인은 사용자 몫입니다.** 이동은 T4, 회전은 T5, 크기는 T6, World/Local 은 T7 입니다.

## 12. 좌표 변환 감사와 재발 방지 (2026-08-26)

기즈모 조작과 액터 픽에서 마우스와 월드 좌표가 어긋나는 문제가 반복되어, 화면과 월드를
변환하는 지점을 전수 감사했습니다.

### 근본 원인

**씬은 뷰포트가 아니라 프레임버퍼 전체에 그려집니다.** `Renderer_render.cpp:164` 가 카메라
투영을 `swapchain.extent`(창 전체) 종횡비로 만들고, `GeometryPass.cpp:521` 이 뷰포트를
`{0,0,extent.width,extent.height}` 로 설정합니다. 즉 렌더는 프레임버퍼 전체를 채우고, 좌우
패널이 그 위에 UI 로 덮입니다.

그런데 에디터는 3D 화면을 **패널을 제외한 뷰포트 rect**(`viewportRect`)로 취급합니다. 그래서
마우스↔월드 변환을 뷰포트 rect 기준으로 하면 두 가지가 어긋납니다.
1. **종횡비**: 뷰포트 rect 종횡비가 프레임버퍼 종횡비와 달라 원근 투영의 X 가 틀어집니다.
2. **화면 매핑**: NDC→화면을 패널만큼 안으로 들어간 rect 로 매핑해 실제 렌더와 어긋납니다.
오차는 화면 중심에서 멀수록 커집니다.

이 결함이 기즈모(`EditorGizmo`), 액터 픽(`pickActor`) 두 곳에서 각각 나타났습니다.

### 감사 결과

화면↔월드 변환 지점 49개를 전수 조사했습니다. **기즈모와 pickActor 를 고친 뒤 남은 좌표
결함은 없습니다.** 모든 `projMatrix(` 호출이 프레임버퍼/swapchain 종횡비를 쓰고,
모든 `viewportRect` 사용은 게이팅(마우스가 3D 영역 안인가) 전용입니다.

오탐으로 걸러낸 것(전부 정상): 카메라 회전·팬은 마우스 **델타**만 쓰므로 좌표계와 무관합니다.
스플리터·HSlate 포인터·`viewportRect` 게이팅은 UI 판정이라 윈도 좌표가 맞습니다.

### 재발 방지 (권고 A 구현)

마우스↔월드 변환에 필요한 좌표를 `WorldViewport` 값 객체 하나로 묶었습니다
(`EditorGizmo.hpp`). 유일한 생산자는 `EditorApp::worldVP(mx,my,winW,winH)` 이고,
`pickActor`·`gizmo_.tick`·`gizmo_.handleDrag` 는 **오직 이 구조체로만** 좌표를 받습니다.
그래서 "뷰포트 rect + 윈도 마우스" 를 실수로 넘기는 것이 **구조적으로 불가능**합니다.
캐시를 없애 stale 을 불가능하게 만든 것(DEF-49)과 같은 방식입니다.

### 미확인 (정적 추적 한계)

- **`getFramebufferSize` == `swapchain extent` 가정**: 에디터는 GLFW 를, 렌더는 swapchain 을
  각각 씁니다. 통상 같지만 리사이즈 직후 한 프레임에서 갈릴 수 있고, 그 등가성은 코드로
  보장돼 있지 않습니다. 완전한 해결은 렌더가 실제 렌더 extent 를 노출하고 에디터가 그것을
  쓰는 것입니다(권고 B). 지금은 가정으로 두고 `worldVP` 주석에 명시했습니다.
- **근본 해결(권고 C)**: 씬을 뷰포트 크기의 오프스크린 타깃에 렌더하면 이 결함 부류가
  사라집니다. 그때는 모든 월드 변환이 반대로 `viewportRect` 기준이 되며, `worldVP` 단일
  진입점이 그대로 전환 지점이 됩니다. 앞서 Quest 조사의 A-1(데스크톱 GPU 39% 절감)과
  같은 작업입니다.
