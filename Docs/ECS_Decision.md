# ECS 도입 보류 결정 문서 (2026-09-08)

Haruka 는 ECS(Entity-Component-System)가 아니라 **Actor + Component 컴포지션**입니다.
이 문서는 그 선택이 무지나 회피가 아니라 **측정과 순서 판단**의 결과임을 기록하고,
언제 이 결정을 뒤집어야 하는지를 수치로 못박습니다.

같은 형식의 선행 문서: [Memory_Allocator_Decision.md](Memory_Allocator_Decision.md),
[Vulkan_Single_RHI_Decision.md](Vulkan_Single_RHI_Decision.md).

---

## 0. 현재 구조

- `World` 가 `unique_ptr<Actor>` 를, `Actor` 가 `unique_ptr<Component>` 를 소유합니다.
- 컴포넌트 조회는 `std::type_index` 해시 캐시로 O(1).
- Unity 식 `activeSelf` / `activeInHierarchy`, 활성 전이 시 서브트리 `onEnable`/`onDisable` 전파.
- 틱 중 파괴 요청은 지연 큐로 미룹니다.

프로덕션 컴포넌트는 5종(StaticMesh, Light, Camera, Audio, RigidBody)입니다.

---

## 1. 측정 (2026-09 실측)

**적용 범위: 데스크톱(RTX 3080) 단일 관측입니다.** Quest Pro 에서 재측정하기 전까지
이 판단의 유효 범위는 데스크톱에 한정됩니다. 아래 트리거도 그 전제 위에 있습니다.

| 항목 | 값 | 의미 |
|---|---|---|
| Frame | 2.02 ms | |
| Extract(드로우 추출) | 0.01 ms | 프레임의 0.5% |
| Tick(월드) | 0.00 ms | 측정 한계 이하 |
| ImgFence | 1.57 ms | GPU Total 1.52 와 근사 → **GPU 바운드** |
| AO + Bloom | 0.84 ms | GPU 의 55% |

여기에 구조적 사실이 겹칩니다. **프로덕션 컴포넌트 5종 중 `tick(float)` 을 오버라이드한 것이
0개**입니다. 즉 `World::tick` 은 아무것도 하지 않는 가상 호출의 반복이고, 편집 모드에서는
`isPlaying()` 게이트에 막혀 호출조차 되지 않습니다.

ECS 의 주된 이득은 **동종 데이터를 대량 순회할 때의 캐시 지역성과 병렬화**입니다.
지금 그 순회는 프레임의 0.5% 안에 들어 있고, 지배항은 화면 해상도에만 비례하는
스크린스페이스 포스트 프로세싱입니다. **엔티티 수와 원리적으로 무관한 비용입니다.**

## 2. "수천 개 파편" 목표는 실재합니다

이 결정은 목표를 숨기고 내린 것이 아닙니다.
[Engine_Strategy_Evaluation.md](Engine_Strategy_Evaluation.md) 가 이 엔진의 차별화 명제로
**"Quest Pro에서 수천 개의 파편을 90fps 무중력으로 탐험하는 우주 VR 샌드박스"** 를 선언하고
`DebrisFieldComponent(수천 개 부유 파편장)` 를 명시합니다.
[Layer_Architecture.md](Layer_Architecture.md) 는 그것이 `kMaxDraws = 1024` · `kMaxBodies = 4096`
이중 상한에 걸린다는 점까지 적어 두었습니다.

그럼에도 지금 착수 근거가 되지 않는 이유는 셋입니다.

**(1) 순서가 다릅니다 — 결정적 비대칭.**
파편장을 막는 것은 데이터 배치가 아니라 **GPU 제출 경로**입니다.
`instanceCount = 1` 이 다섯 곳에 리터럴로 박혀 있고 `GeometryPass::DrawItem` 에는
인스턴스 멤버 자체가 없습니다.

> ECS 를 넣고 인스턴싱을 안 하면 파편장은 안 되고, 인스턴싱만 하고 ECS 를 안 하면 됩니다.

파편장이 실제로 착수될 때조차 **첫 작업은 ECS 가 아닙니다.**

**(2) 자체 로드맵이 4단계에 배치했습니다.**
같은 문서가 우주 도메인을 4단계 중 4단계에 두었고, 그 이유를 "지금 코드에는 Layer 2 가 소비할
배관이 없기 때문"이라고 적었습니다. [Roadmap.md](Roadmap.md) 의 다음 착수 목록
(Light Channels, CSM, 스테레오, 3D UI)에는 파편장도 인스턴싱도 없습니다.

**(3) 규모가 확정되지 않았습니다.**
[Deep_Space_VR_Specification.md](Deep_Space_VR_Specification.md) 는 "실제 타깃 콘텐츠는
수 km 규모의 난파선"이라며 규모 주장을 이미 한 번 축소 정정했습니다.
손익분기 추정은 아래와 같습니다.

| 엔티티 수 | SoA 전환 절감(추정) |
|---|---|
| 1,000 | 0.035 ms |
| 10,000 | 0.30 ms |
| 100,000 | 흔히 인용되는 4~5배 차이가 나타나는 구간 |

**파편이 300~500개로 착지하면 이 조건은 발화하지 않은 것입니다.**

## 3. "ECS 가 대세" 라는 전제

실제 채택 현황과 다릅니다.

| 엔진 | 근간 구조 | ECS 위치 |
|---|---|---|
| Unreal | AActor + UActorComponent | Mass — 군중 전용 서브시스템 |
| Unity | GameObject | DOTS — 하이브리드로 병존 |
| Godot | 노드 트리 | 공식적으로 거부 사유 공표 |
| O3DE | 엔티티 + 컴포넌트 | — |

주요 엔진 넷이 Haruka 와 같은 계열이고, ECS 는 그 안에서 **격리된 서브시스템**으로 삽니다.
순수 ECS 는 Bevy 같은 비교적 새로운 엔진들의 선택입니다.

참고로 **VR 은 ECS 에 반대하는 근거가 아닙니다.** 오히려 90Hz 스테레오는 프레임 예산이
11.1 ms 로 빡빡해 CPU 효율이 더 중요해지는 환경이고, Unity DOTS 는 VR 프로젝트에서 쓰입니다.
"VR 이라서 ECS 가 필요 없다"는 서술은 이 문서 어디에도 두지 않습니다.
정확한 진술은 **"VR 을 실제로 붙여 측정하기 전에는 판단할 근거가 없다"** 입니다.

## 4. 결정

**ECS 를 도입하지 않습니다.** ECS 가 약속하는 이득 중 이 프로젝트에 실제로 필요한 것은
전부 Actor + Component 모델 안에서 회수됩니다. 대신 아래를 **트리거 작업**으로 둡니다
(선제 작업이 아니라, 해당 조건이 발생하는 커밋에 얹습니다).

| 작업 | 착수 시점 |
|---|---|
| 컴포넌트 타입 레지스트리 (`SceneSerializer` 3곳 + 디테일 패널 `dynamic_cast` 5분기) | 6번째 컴포넌트 타입을 추가하는 커밋에서 |
| 추출 경계를 값 SoA 로 (`Renderer_render.cpp` 의 `owner->` 3지점 제거) | 스테레오 작업이 렌더 뷰 구조를 어차피 바꿀 때 그 작업에 얹어서 |
| `ctx_.selected` 를 id 화 (42지점, 전부 한 파일) | 에디터를 어차피 만질 때 |
| 인스턴싱 (DEF-16) | 파편장 착수 시 **첫 번째** 작업 |

**명시적으로 하지 않을 것**

- `World` 에 타입별 컴포넌트 사본 배열(`meshes_`/`lights_`)을 두지 않습니다.
  정본(`Actor::components`)과 사본을 두 곳에서 관리하는 파생 상태이고, 이 저장소는 정확히 그
  유형(DEF-49 stale 캐시)으로 이미 당해 캐시를 걷어낸 이력이 있습니다. 얻는 것은 프레임당
  해시 조회 100여 회 제거인데, 그 전체가 Extract 0.01 ms 안에 들어 있어 관측되지 않습니다.
- `worldMatrix` 캐시 재도입. 재도입 조건은 `Actor.cpp` 주석이 이미 "계층이 수천 개로 커져
  프로파일러가 이 순회를 지목하면"으로 못박아 두었습니다.

## 5. 결정을 뒤집어야 할 신호 (트리거)

**모든 수치 트리거는 타깃 하드웨어에서 잰 값이어야 합니다.** 데스크톱 수치는 판정 자격이 없습니다.

1. **Quest Pro 90Hz 스테레오 11.1 ms 예산에서** `FrameTimings` 의 Extract 또는 Tick 이
   프레임의 **10%** 를 넘을 때 (현재 데스크톱 0.5% / 0.0%).
2. 시뮬레이션 틱이 [Threading.md](Threading.md) 가 스스로 정한 잡 시스템 착수 트리거인
   **2~3 ms** 에 닿을 때 (현재 0.00 ms). 이 전에는 ECS 의 최대 구조적 이득(컴포넌트 접근 집합
   기반 자동 잡 그래프)을 소비할 곳이 없습니다.
3. 프로덕션 컴포넌트가 `tick(float)` 을 오버라이드하기 시작하고, 그 틱이 **상시 수천 개**
   엔티티에서 도는 형태일 때 (현재 5종 중 0개).
4. **인스턴싱(DEF-16)이 이미 해결된 뒤에** `kMaxDraws = 1024` 상한에 실제로 닿을 때.
   순서가 뒤바뀌면 ECS 는 상한에 막혀 이득이 0 입니다.
5. `DebrisFieldComponent` 설계가 확정되면서 파편 개수가 **수천 개 이상으로 남고**, 각 파편이
   단순 파티클이 아니라 물리·수명·상호작용을 갖는 게임플레이 엔티티로 확정될 때.
6. 컴포넌트 타입이 **6종을 넘어설 때** — 단 이것은 ECS 트리거가 아니라 **타입 레지스트리
   트리거**입니다. 레지스트리 하나로 닫히며 ECS 를 요구하지 않습니다.
7. **결정론적 시뮬레이션이나 롤백 넷코드**가 범위에 들어올 때. Overwatch 가 ECS 를 택한 실제
   동기가 캐시 성능이 아니라 이것이었습니다. 현재 Haruka 에는 네트워킹 서브시스템이 없습니다.

**역방향 트리거(도입을 더 미뤄야 할 신호)** — 미해결 결함이 줄지 않거나, 로드맵의
스테레오·CSM·Light Channels 가 계속 밀릴 때. 아키텍처 리팩터링은 결함 잔고가 줄고 로드맵이
진행 중일 때만 감당할 수 있습니다.

## 6. 도입하게 될 경우의 단서

트리거가 발화해 실제로 착수하더라도 **전면 마이그레이션은 배제합니다.** 에디터·직렬화·물리·
오디오·기즈모를 쿼리 기반으로 재작성하기 전까지 엔진이 동작하지 않는 무기능 구간이 생기고,
1인 개발에서 그 구간은 곧 실패 구간입니다. 지켜야 할 것들입니다.

- **인스턴싱이 먼저입니다.** 이 순서를 바꾸면 ECS 를 넣어도 상한에 막혀 이득이 0 입니다.
- **계층은 ECS 로 옮기지 마십시오.** `parent_`/`children_`/`activeInHierarchy`/
  `refreshSubtreeActive` 를 `Actor` 에 남깁니다. Unity DOTS 도 Bevy 도 계층을 사후에 되붙여야
  했고, 이 저장소는 그 의미론에 이미 값을 치렀습니다(테스트 7시나리오).
- **리플렉션이 단일 결정점입니다.** `Reflect.hpp` 의 `XPROP_*` 가 컴포넌트 주소를 캡처하는 한,
  밀집 저장이 컴포넌트를 **이동시키는 순간** 현재의 purge(포인터 비교)는 "파괴가 아니라 이사"를
  잡지 못합니다. DEF-55 가 그 구조의 첫 청구서였습니다.
- 밀집 저장을 하더라도 아키타입이 아니라 **sparse-set**(EnTT 계열)으로. 구조 변경 시 청크
  이동·쿼리 캐시 무효화 비용을 지불하지 마십시오.
- 외부 핸들 수명 주의 — Jolt `BodyID`, `ma_sound*` 는 `Component::onDestroy` 하나에 수명이
  묶여 있습니다. 컴포넌트를 이동시키면 이동 생성자를 명시 정의해 이중 해제를 막아야 합니다.

**차라리 격리 도입이 낫습니다.** 파편·파티클처럼 계층·직렬화·인스펙터를 요구하지 않는 신규
워크로드라면, `Actor` 를 전혀 쓰지 않는 전용 SoA 시스템을 별도 디렉터리에 격리하고 값 배열로만
렌더러와 합류시키십시오. 기존 코드는 한 줄도 마이그레이션하지 않고, 실패하면 디렉터리 하나
삭제로 회수됩니다. UE 의 Mass·Niagara, Unity 의 SubScene 이 정확히 이 형태입니다.

## 7. 성능이 목적이라면 방향이 다릅니다

GPU 지배항은 AO + Bloom 0.84 ms(GPU 의 55%)이고, VR 예산 추정에서 SSAO + Bloom + 톤매핑이
11.1 ms 의 대부분을 차지합니다. 전부 **화면 해상도에만 비례하는 스크린스페이스 비용**이라
엔티티 수와 무관합니다. 같은 노력을 SSAO 샘플 수와 해상도 조정에 쓰면 효과가 훨씬 큽니다
(경로는 [Rendering 관련 문서](README.md)에 이미 특정되어 있습니다).
