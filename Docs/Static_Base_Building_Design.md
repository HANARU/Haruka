## 0. 범위와 전제

- **정적 구조물**: 한 번 지은 기지 모듈(통로 · 방 · 해치 등)은 움직이지 않습니다. 기지 전체가 움직이는 이동형 기지(움직이는 격자)는
  범위에서 뺍니다.
- **대상 기기**: Meta Quest Pro 단독 실행(Snapdragon XR2+ Gen 1, Adreno 650). 90Hz 기준 프레임 예산은 11.1ms 입니다.
- **계층 구분**: 모듈 정의 · 연결 규칙 · 건설 도구 · 방 연결 그래프는 Layer 2 입니다. 콜라이더 종류 · 바디 일괄 추가 · 컬링 가시성
  지점 · 품질 설정처럼 다른 도메인에서도 쓸 기능은 Layer 1 에 넣습니다(4절).
- **측정 전제**: 아래의 성능 판단은 Quest 실측 전입니다. 이 PC 의 측정 기록은 RTX 3080 데스크톱 몇 건뿐입니다.

## 1. 정적 구조물로 정해서 얻는 것

### 1-1. 물리: 정적 레이어

**현재 상태.** `PhysicsSystem` 은 정적 · 움직이는 두 레이어를 씁니다. RigidBody 의 `motion` 을 Static 으로 두면 정적 레이어에 들어갑니다.

**얻는 것.** Jolt 는 정적 바디를 시뮬레이션하지 않습니다. Haruka 는 정적 레이어를 별도 브로드페이즈 레이어에 두고, 레이어 필터로
정적 바디끼리는 충돌을 검사하지 않게 합니다(`PhysicsSystem.cpp` 의 `ObjLayerPairFilter`). 그래서 모듈 수가 늘어도 매 스텝의 비용은
거의 늘지 않습니다. 남는 비용은 동적 바디(파편 · 플레이어 손)가 모듈에 닿을 때의 접촉 계산과 레이캐스트입니다.

**주의할 점.** 지금은 바디를 반복문에서 하나씩 `AddBody` 합니다. 바디를 하나씩 넣으면 브로드페이즈 트리가 고르지 않게 자랍니다. 대량으로
넣을 때는 Jolt 의 `AddBodiesPrepare` · `AddBodiesFinalize` 로 묶어 넣고, 씬을 불러와 기지 전체를 올린 뒤에는 `OptimizeBroadPhase` 를 한
번 부릅니다. 런타임에 모듈 하나를 지을 때마다 `OptimizeBroadPhase` 를 부르지는 않습니다(전체 트리를 다시 짓는 비싼 호출).

### 1-2. 월드 행렬

**현재 상태.** `Actor::worldMatrix` 는 캐시 없이 부모 체인을 재귀로 곱합니다. 렌더러는 매 프레임 메시마다 이 값을 구해 transform 행에
씁니다(계층과 상관없이 매 프레임 일어나는 비용).

**판단.** 모듈을 월드 바로 아래에 평탄하게 두어도 아끼는 것은 부모 곱셈 한 번뿐이라 효과가 작습니다. 기지 저장 · 편집 편의를 위해
"기지 루트 액터 아래에 모듈 한 단계"로 묶기를 권장합니다. 정적 모듈의 행렬 계산과 행 업로드 자체를 건너뛰려면 렌더러에 "정적 행 캐시"를
따로 만들어야 하며, 이는 모듈이 수천 개 규모가 되었을 때 실측한 뒤 판단합니다.

### 1-3. 라이팅

**현재 상태.** 매 프레임 `hlight::select` 가 어느 눈의 절두체와도 영향 구가 겹치지 않는 점광원 · 스팟을 거르고, 상한(`render.maxLights`)을
넘으면 방향광을 먼저, 나머지는 거리/반경 순으로 고릅니다. 꺼진 라이트 컴포넌트와 비활성 액터의 라이트는 후보에 들어가지 않습니다.
구운 라이팅(라이트맵)과 실내 · 실외 판정은 없습니다.

**정적 구조로 할 수 있는 것.**
- 방(모듈) 단위로 라이트 컴포넌트를 켜고 끕니다. Layer 2 가 지금 API 로 할 수 있습니다.
- 2-2 의 방 가시성과 묶어, 보이지 않는 방의 라이트를 끄면 픽셀당 순회하는 라이트 수가 줄어듭니다.
- 라이트맵 굽기는 이 지침의 범위 밖입니다(도입 여부는 6절).

## 2. Quest 타일 GPU 렌더링 전략

### 2-1. 후처리 예산

**현재 상태.**
- 매 프레임 SSAO(선형 깊이 → 반해상도 64 샘플)와 Bloom(문턱값 1/2 해상도 → 다운샘플 4회 → 업샘플 4회)을 그립니다. 끄는 설정이 없습니다
  (`PostPass` 의 켜기 플래그가 1 로 고정).
- **SSAO 는 MSAA 깊이를 샘플링합니다.** 그래서 메인 패스가 MSAA 깊이를 매 프레임 메모리에 STORE 합니다. 2-K 절은 이를 프레임당 약 110MB 의
  대역폭 항목으로 꼽았습니다.
- 2-K 절은 SSAO 를 상수 조정(64 → 24 탭, 1/4 해상도 등)만으로 예산의 5 ~ 13% 까지 줄일 수 있다고 봤습니다.

**지침.**
- **Quest 기본값은 SSAO 끄기를 권장합니다**(6절 1번에서 확정). 정적 모듈의 구석 음영은 모델의 glTF occlusion 텍스처로 구워 넣습니다. 엔진은 이 텍스처를 이미 읽어
  간접광(IBL)에만 곱합니다.
- SSAO 를 끄면 MSAA 깊이의 STORE 를 DONT_CARE 로 바꾸고 깊이 이미지도 TRANSIENT 로 둘 수 있습니다. 이 작업은 DEF-06(MSAA 지연 할당)과 함께
  합니다. **다만 SSAO 만 깊이를 읽는 것은 아닙니다.** 렌더 확장의 메인 패스 뒤 지점(`AfterScene`)이 MSAA 깊이(`depthView`)를 확장에
  넘겨주므로, 깊이를 저장하지 않으려면 그 계약도 바꿔야 합니다(예: 깊이를 쓰는 확장이 없을 때만 저장 생략). 방식은 6절에서 정합니다.
- 조정한 SSAO 와 Bloom 을 Quest 에서 켤지는 실측으로 정합니다.
- 정점 색으로 음영을 넣는 방법은 권장하지 않습니다. 정점 형식(위치 · 법선 · UV · 탄젠트)에 색 속성이 없어 모든 파이프라인을 고쳐야 합니다.

**필요한 Layer 1 작업.** 품질 설정(예: `Config/engine.ini` 에 SSAO · Bloom 켜기/끄기)과, 끌 때 패스를 생략하고 깊이 저장 방식을 바꾸는 렌더
패스 변형.

### 2-2. 방 · 해치 가시성(포털)

**현재 상태.**
- 컬링은 CPU 에서 바운딩 구 대 6평면이고, 두 눈 중 하나라도 통과하면 그립니다. 가려짐(오클루전)은 판정하지 않습니다.
- 메인 패스에 깊이 프리패스가 있습니다. 컬러 서브패스는 깊이를 쓰지 않고 `LESS_OR_EQUAL` 로 비교하므로, 불투명 셰이딩은 픽셀당 한 번으로
  이미 묶여 있습니다. 벽 너머 물체가 남기는 비용은 정점 처리 · 프리패스 래스터 · 드로우 수입니다.

**지침.** 모듈을 방, 해치를 포털로 두는 연결 그래프를 만듭니다. 카메라가 있는 방에서 출발해 열린 해치의 화면 사각형을 거쳐 보이는 방만
그립니다(고전 포털 엔진, Unity Occlusion Portal 과 같은 방식). 기지가 정적이므로 그래프는 모듈을 짓거나 해치 상태가 바뀔 때만 갱신합니다.
효과는 Quest 실측으로 확인합니다.

**필요한 Layer 1 작업.** 렌더러 컬링 단계에 Layer 2 가 가시성 결과를 넣을 지점이 없습니다. 지금 Layer 2 가 쓸 수 있는 수단은 둘뿐이고 둘 다
맞지 않습니다.
- 액터 끄기: 물리 바디와 소리까지 함께 꺼집니다.
- StaticMesh 의 `visible`: 직렬화되는 편집 값이라 매 프레임 계산 결과를 담는 자리로 쓰기에 맞지 않습니다.

컬링 단계에서 부르는 가시성 질의(액터 또는 묶음 단위 마스크)를 Layer 1 에 두어야 합니다. 형태는 6절에서 정합니다.

### 2-3. 반투명(창문 · 건설 프리뷰)

**현재 상태.** 반투명은 메인 패스 세 번째 서브패스에서 뒤에서 앞으로 정렬해, 목록 전체를 뒷면만 한 번 · 앞면만 한 번 그립니다. 평평한 유리는
카메라를 향한 면만 그려지므로, 면 하나짜리 메시라면 두 번 그려지지 않습니다. 반투명은 자동 인스턴싱으로 묶이지 않고, glTF `alphaMode = MASK` 는 지원하지 않습니다.

**채택하지 않는 방법.** 원본 가이드는 건설 프리뷰를 디더링(셰이더에서 체커보드로 `discard` 하는 알파 클리핑)으로 그리라고 했습니다. 이 방법은
쓰지 않습니다.
- 모바일 GPU 지침들은 셰이더 `discard` 가 이른 깊이 판정을 약하게 만든다는 이유로 피하라고 권합니다.
- Haruka 의 깊이 프리패스는 알파를 모르므로, 디더링한 메시는 프리패스에도 같은 `discard` 를 넣어야 합니다.

**지침.**
- 건설 프리뷰는 렌더 확장 지점(반투명 끝 또는 톤매핑 뒤)에서 외곽선 · 격자 같은 **선**으로 그립니다.
- 면이 꼭 필요하면 작은 면적의 반투명으로 그립니다. 디더링이 꼭 필요하면 MSAA 4x 를 이미 쓰고 있으므로 alpha-to-coverage 를 씁니다.
- 큰 유리창은 화면을 덮는 면적만큼 PBR 셰이딩을 한 번 더 하므로, 겹치는 유리 수를 제한하고 유리 전용 단순 셰이더를 검토합니다. 지금 머티리얼
  체계에는 셰이더 변형이 없어 이것은 Layer 1 작업입니다.

### 2-4. 타일 메모리와 멀티뷰

- **DEF-06**: MSAA 컬러 이미지는 이미 TRANSIENT 용도 · DONT_CARE 저장이지만 `LAZILY_ALLOCATED` 메모리를 쓰지 않습니다. MSAA 이미지는 1GB 힙
  (Zone B)에서 할당되는데, 이 힙의 메모리 타입은 HOST_VISIBLE 형식이라 `LAZILY_ALLOCATED` 가 될 수 없습니다. 따라서 MSAA 이미지를 힙 밖에서
  따로 할당해야 합니다. 깊이까지 지연 할당하려면 2-1 처럼 SSAO 의 깊이 읽기를 없애야 합니다.
- **멀티뷰**: 지금은 눈마다 두 번 그립니다. 셰이더 · UBO 가 두 눈 기준이라 이식 때 뷰 번호만 바꿔 켭니다. 이득은 주로 명령 기록 · 드라이버
  비용이 절반으로 주는 것입니다.
- 둘 다 이미 Quest 이식 목록에 있습니다.

### 2-5. 깊이 프리패스 재평가

타일 GPU 에서는 깊이 프리패스가 정점 처리와 비닝을 두 번 하게 만듭니다. Adreno 는 하드웨어로 이른 깊이 거르기를 하므로 PC 와 득실이 다를 수
있습니다. 기지 모듈로 정점 수가 늘면 차이가 커지므로 Quest 실측 항목으로 둡니다.

## 3. 건설 생명주기: 멈칫 방지

VR 에서는 한 프레임만 멈춰도 멀미로 이어집니다. 런타임에 모듈을 지을 때 디스크 읽기 · 파이프라인 생성 · 큰 물리 갱신이 그 프레임에 일어나지
않게 합니다.

### 3-1. 건설용 에셋의 사전 상주

**현재 상태.** 에셋 로딩은 메인 스레드에서 동기로 합니다. `AssetManager` 는 모델을 경로별로, 절차 도형을 기술자 키별로 캐시하므로 같은 것을 다시
요청하면 디스크를 읽지 않고 GPU 에 다시 올리지도 않습니다. 같은 지오메트리 · 머티리얼의 불투명 메시는 자동 인스턴싱으로 드로우 하나에 묶입니다.

**지침.**
- 건설에 쓰는 모듈 종류는 한정되어 있으므로, 씬 시작 때(로딩 화면처럼 멈춰도 되는 시점) 모든 모듈 에셋을 한 번씩 불러 둡니다.
- 런타임 건설은 `World::spawnActor` 로 액터를 만들고 같은 모델 경로를 가리키게 합니다. 디스크 읽기 · 업로드 없이 자동 인스턴싱에 합류합니다.
- 모듈 에셋 총량이 Zone B(896MB) 예산에 들어가야 합니다. DEF-42 로 힙이 줄면 B 도 줄어듭니다(5절).
- `.gasset` 캐시는 첫 실행 때 만들어집니다. Quest 배포 때는 미리 만든 캐시를 함께 넣는 방법을 이식 때 정합니다.

### 3-2. 물리 바디 추가

**현재 상태.**
- RigidBody 는 셰이프 하나(Box · Sphere · Capsule)만 갖고, 액터마다 하나입니다. Play 중에 지연 생성되며, 바디를 하나씩
  `AddBody` 합니다.
- 바디를 **제거할 때만** 그 영역(+5cm) 안의 바디를 깨웁니다(DEF-80). **추가할 때는 아무것도 깨우지 않습니다.** 그래서 잠든 파편이 있는 자리에
  모듈을 지으면 파편이 깨어나지 않고 벽에 박힌 채 남습니다.

**지침.**
- 모듈 하나를 정적 바디 하나로 만듭니다. 셰이프는 벽 · 바닥 · 천장 상자를 묶은 `StaticCompoundShape` 나 정적 바디용 `MeshShape`(충돌 전용
  메시)입니다. 어느 쪽을 쓸지는 6절에서 정합니다.
- 여러 모듈을 한 번에 지을 때는 1-1 의 일괄 추가를 씁니다.
- 모듈을 추가한 뒤 그 영역 안의 동적 바디만 `ActivateBodiesInAABox` 로 깨웁니다(제거 경로와 같은 방식). 깨어난 바디가 벽에 깊이 박혀 있으면
  Jolt 의 침투 복구가 세게 밀어낼 수 있으므로, 건설 가능 판정에서 겹치는 동적 바디가 있으면 짓지 못하게 하는 규칙도 검토합니다. 지금 물리 API
  에는 구 겹침 질의만 있어 상자 겹침 질의가 필요합니다.

**필요한 Layer 1 작업.** 복합 · 메시 콜라이더, 바디 일괄 추가, 추가할 때 영역 깨우기, 상자 겹침 질의.

### 3-3. 파이프라인 사전 생성

**현재 상태.**
- 렌더 확장은 등록하는 즉시 `create` · 크기 의존 자원 · 파이프라인을 만들고 다음 프레임부터 그립니다.
- 파이프라인 캐시를 시작할 때 `pipeline_cache.bin` 에서 읽고 종료할 때 저장합니다.
- 뷰포트 통계의 재생성 횟수는 **스왑체인과 렌더 타깃의 재생성** 횟수(창 · 뷰포트 크기 변경 등)이며 파이프라인 생성과는 관계가 없습니다.

**지침.**
- 건설 전용 확장(프리뷰 · 격자)은 게임 모듈이 시작할 때(`onStart`) 등록하고, 건설 모드에서는 확장의 `record` 가 그릴지만 바꿉니다. 건설 모드에
  들어갈 때 등록하면 그 프레임에 파이프라인을 만듭니다.
- Quest 에서는 파이프라인 캐시 경로가 실행 폴더 상대 경로라 앱 저장소 경로로 옮겨야 합니다(이식 때 확인).

## 6. 구현 때 정할 것

1. Quest 의 SSAO 기본값: 끄고 AO 텍스처로 대체(권장) 또는 조정한 SSAO 유지. 끌 때 렌더 확장 `AfterScene` 지점의 깊이 제공을 어떻게
   할지(깊이를 쓰는 확장이 있을 때만 저장, 또는 Quest 에서는 깊이를 넘기지 않음)도 함께 정합니다.
2. 컬링 가시성 질의의 형태: 액터 단위 마스크, 자동 인스턴싱 묶음 단위, 확장 인터페이스 중 무엇으로 할지.
3. 모듈 콜라이더: `StaticCompoundShape`(상자 묶음) 또는 `MeshShape`(충돌 메시).
4. 건설 자리에 동적 바디가 있을 때: 짓지 못하게 막을지, 깨워서 밀어낼지.
5. DEF-42 의 힙 축소 방식.
6. 구운 라이팅(라이트맵)을 도입할지(지금은 범위 밖).
7. VR 글자 표시 방식(SDF 등). 3D UI 패널 설계와 함께 정합니다.
