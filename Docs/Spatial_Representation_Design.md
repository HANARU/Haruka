# 엔티티 공간 표현 설계

**작성 2026-08-26.** 이 문서는 트랜스폼을 가진 모든 엔티티(라이트, 카메라, 3D UI, VFX,
오디오, 트리거 등)가 뷰포트에서 **일관되게 배치·선택·조작·시각화**되도록 하는 개념을
정리합니다. 트랜스폼 자체의 버그와 기즈모는 [Transform_Design.md](Transform_Design.md)가
다루며, 이 문서는 그 위에 얹는 엔티티 무관 공간 계층을 다룹니다.

**코드로 넘어가기 전 검토용**입니다.

---

## 1. 문제

지금은 세 가지 능력이 전부 `StaticMeshComponent`에 묶여 있습니다.

| 능력 | 현재 구현 | 문제 |
|---|---|---|
| **선택(픽)** | `pickActor`가 `StaticMeshComponent`가 있는 액터만, 메시 AABB로 판정 | 라이트·카메라·오디오는 뷰포트에서 클릭 선택이 안 됨 |
| **바운드** | 기즈모 박스가 메시 AABB, 컬링이 메시 bound sphere | 메시 없는 엔티티는 바운드가 없어 박스·프레이밍·컬링에서 빠짐 |
| **시각화** | 없음 | 라이트 방향, 카메라 절두체, 오디오 반경이 화면에 보이지 않음 |

반면 **조작(기즈모)은 이미 `Actor::transform`만 보므로 엔티티에 무관합니다.** 즉 조작
계층은 이미 올바르고, 선택·바운드·시각화 계층만 메시에 묶여 있습니다.

**앞으로 추가될 엔티티가 전부 이 문제를 겪습니다.** 3D UI 패널, VFX 이미터, 오디오 존,
스폰 지점, 트리거 볼륨, 스플라인은 모두 트랜스폼을 갖고 뷰포트에서 배치되어야 하는데,
컴포넌트마다 픽·바운드·시각화를 따로 특수 처리하면 종류가 늘 때마다 세 곳을 고쳐야 합니다.

## 2. 개념 계층 분리

엔티티의 공간 표현을 네 계층으로 나눕니다. 각 계층이 무엇에 의존하는지 명확히 합니다.

| 계층 | 무엇 | 현재 상태 |
|---|---|---|
| **위치(Transform)** | 로컬 트랜스폼, 계층에서 유도한 월드 | 완성. 모든 액터가 가짐. 엔티티 무관 |
| **바운드(Bounds)** | 로컬 공간 범위. 픽·컬링·프레이밍·기즈모 박스의 근거 | 메시에만 있음. **추상화 필요** |
| **시각화(Editor Visual)** | 아이콘과 와이어 영향 범위. 보이고 잡히게 함 | 없음. **신설 필요** |
| **조작(Manipulation)** | 기즈모 이동·회전·크기 | 완성. 엔티티 무관 |

**핵심 판단**: 위치와 조작은 이미 엔티티 무관이므로 건드리지 않습니다. 바운드와 시각화를
엔티티 무관 추상화로 올리면, 픽은 바운드를 질의하는 한 경로로 통일됩니다.

---

## 3. 제안 — 컴포넌트가 자기 공간 표현을 알린다

컴포넌트 기반 클래스에 가상 훅을 추가하여, 각 컴포넌트가 자기 바운드와 시각화를
스스로 제공하게 합니다. 에디터(픽·기즈모·프레이밍)와 렌더러(컬링)는 이 훅을
**한 방식으로만** 질의합니다. 컴포넌트를 특수 처리하는 분기가 사라집니다.

### 3-1. 로컬 바운드 제공자

```cpp
// Component (가산)
// 컴포넌트가 자기 로컬 공간 바운드를 알립니다. 없으면 false.
// 픽, 컬링, 프레이밍, 기즈모 박스가 전부 이 하나를 질의합니다.
virtual bool localBounds(glm::vec3& outMin, glm::vec3& outMax) const { return false; }
```

- `StaticMeshComponent` → 메시 AABB.
- `LightComponent`(Point/Spot) → 영향 범위(range 구, spot 원뿔의 AABB). Directional → 없음(아이콘만).
- `CameraComponent` → 절두체 AABB 또는 없음(아이콘만).
- `AudioComponent` → 감쇠 반경 구.
- 3D UI 패널 → 패널 사각형.
- VFX 이미터 → 이미터/방출 볼륨 또는 없음(아이콘만).

액터 전체 바운드 = 컴포넌트 바운드의 합집합. 바운드를 알리는 컴포넌트가 하나도 없으면
**아이콘 픽**으로 넘어갑니다(3-3).

### 3-2. 에디터 시각화

메시 없는 엔티티가 보이고 잡히도록, 컴포넌트가 에디터 전용 시각을 제공합니다.
두 종류입니다.

- **아이콘**: 화면상 고정 크기의 빌보드(전구, 카메라, 스피커 아이콘). 항상 같은 픽셀
  크기라 멀리 있어도 잡을 수 있습니다. 화면 공간 원판 판정으로 픽합니다.
- **와이어 영향 범위**: 라이트 range 구, spot 원뿔, 카메라 절두체, 오디오 반경. 선택 시
  또는 항상 옅게 라인으로 그립니다.

```cpp
// Component (가산)
// 에디터 전용 시각화. 선택 여부에 따라 다르게 그릴 수 있음.
// dl 은 라인/삼각형/아이콘을 모으는 드로우 리스트 (기즈모의 라인·삼각형 오버레이 재사용).
virtual void drawEditorVisual(class EditorDrawList& dl, bool selected) const {}
```

이미 만든 기즈모 라인·삼각형 오버레이(`setEditorLines`, `setGizmoTris`)를 그대로 씁니다.
`EditorDrawList`는 그 위에 아이콘(빌보드) 항목을 더한 얇은 수집기입니다.

### 3-3. 픽 통일

`pickActor`가 컴포넌트 종류를 분기하지 않고, 모든 액터에 대해 다음 순서로 질의합니다.

1. 액터의 컴포넌트 중 `localBounds`를 알리는 것이 있으면 **광선-OBB 판정**(현재 메시에
   쓰는 방식을 그대로 일반화). 가장 가까운 것을 고릅니다.
2. 바운드가 없으면 **아이콘 화면 원판 판정**. 액터 원점(또는 아이콘 위치)을 화면에
   투영해 마우스와의 거리로 판정합니다.

메시·라이트·카메라·UI·VFX가 한 픽 경로를 공유합니다.

## 4. 엔티티별 공간 표현 (설계 대상)

| 엔티티 | 바운드 | 아이콘 | 와이어 영향 범위 | 비고 |
|---|---|---|---|---|
| StaticMesh | 메시 AABB | 없음 | 없음 | 이미 됨 |
| Light(Point) | range 구 AABB | 전구 | range 구 | |
| Light(Spot) | 원뿔 AABB | 전구 | 방향 + 원뿔 | direction 필드 시각화(DEF-38 연계) |
| Light(Directional) | 없음 | 태양 | 방향 화살표(원점 고정) | 위치 무의미, 방향만 |
| Camera | 절두체 AABB | 카메라 | 절두체 | 에디터 카메라는 제외 |
| Audio | 반경 구 | 스피커 | 감쇠 반경 | 공간 오디오 파라미터 확인 필요 |
| 3D UI 패널 | 패널 사각형 | 없음 | 패널 테두리 | **VR 핵심.** 두께 얇은 판 |
| VFX 이미터 | 방출 볼륨 또는 없음 | 불꽃 | 이미터 형태 | 후순위 |
| 트리거/스폰 | 볼륨 AABB | 표식 | 볼륨 | 후순위 |

**3D UI 패널을 1급 개념으로 다룹니다.** 이 엔진은 VR 엔진이고, 월드 공간 UI가 핵심
기능이므로, 공간 표현 설계가 처음부터 이것을 담아야 합니다. 패널은 트랜스폼으로 배치되고,
바운드는 얇은 판(예: `[-0.5,0.5]×[-0.5,0.5]×[-ε,ε]`)이며, 픽과 기즈모가 그대로 적용됩니다.

## 5. 트랜스폼 자체의 정리 (핵심 결정 D2)

앞으로 여러 계층(에디터, 물리, 애니메이션, VFX, UI 레이아웃)이 트랜스폼에 씁니다.
그래서 [Transform_Design.md](Transform_Design.md) 4절의 P1(불변식을 타입이 강제)이 다시
문제가 됩니다. 현재는 캐시를 없앴으므로 public 필드가 정확성에는 안전하지만, 엔티티가
늘면 파생 캐시(월드 바운드 캐시, 스트리밍용 씬그래프 더티)를 되살릴 이유가 생길 수 있고,
그때 public 필드는 지뢰가 됩니다.

두 가지 갈래입니다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **가** 현행 유지 | `Actor::transform` public, 세터도 병존 | 변경 0. 지금 동작에 문제 없음 | 나중에 캐시 되살리면 우회 위험 재발 |
| **나** 지금 캡슐화 | `Transform` 필드 private + 접근자, Actor가 `setLocal*`만 노출 | 파생값 캐시를 나중에 넣어도 안전. P1 충족 | 쓰기 지점(에디터·물리·직렬화) 전부 세터 경유로 교체 |

**나를 권고합니다.** "근본적으로 트랜스폼 개념을 정리한다"는 목표에 부합하고, 엔티티가
늘기 전에 하는 것이 가장 쌉니다. 쓰기 지점이 지금은 적습니다(에디터 세 곳, 물리, 직렬화).
캡슐화하면 월드 바운드 캐시 같은 파생값을 나중에 안전하게 넣을 수 있습니다.

## 6. 바운드 집약과 컬링의 관계

- **액터 바운드** = 컴포넌트 `localBounds`의 합집합. 없으면 아이콘용 고정 소형 박스.
- **프레이밍(F 키로 선택 대상 맞춤)**: 액터 바운드를 쓰면 종류 무관하게 동작합니다.
- **컬링**: 지금은 GPU 컴퓨트가 메시 bound sphere를 씁니다(`Renderer_render.cpp:255`).
  개념적으로는 `localBounds`와 같은 근거이지만, 컬링은 GPU 측이라 통합이 큰 작업입니다.
  **지금은 개념만 통일하고, 컬링은 메시 경로를 유지합니다.** 비메시 엔티티(라이트·UI)는
  드로우가 없거나 별도 경로라 GPU 컬링 대상이 아닙니다.

## 7. 아이콘(빌보드) 시스템

메시 없는 엔티티를 보이고 잡히게 하는 최소 요소입니다.

- **렌더**: 화면상 고정 크기의 텍스처 사각형을 액터 위치에 그립니다. 기존 삼각형 오버레이에
  텍스처 샘플링을 더하거나, 단색 원판으로 시작할 수 있습니다.
- **픽**: 액터 위치를 화면에 투영하고 마우스와의 픽셀 거리로 판정합니다. 좌표는 반드시
  `WorldViewport`를 거칩니다([Transform_Design.md](Transform_Design.md) 12절 규약).
- **깊이**: 항상 위에 그릴지(가려지지 않음), 깊이 테스트할지 결정이 필요합니다. 기즈모는
  항상 위에 그립니다. 아이콘도 그 편이 잡기 쉽습니다.
  **[구현 · 2026-08-26]** 아이콘은 기즈모와 같은 오버레이로 그려 **항상 위에** 보입니다(라인 · 기즈모 파이프라인이 깊이 테스트를 끔).

첫 구현은 단색 원판 + 색으로 종류 구분(라이트 노랑, 카메라 파랑, 오디오 초록)으로 충분하고,
텍스처 아이콘은 나중에 얹습니다.

## 8. 구현 순서 (제안)

각 단계가 독립적으로 검증 가능하도록 나눕니다.

1. **트랜스폼 캡슐화(D2가 나일 때).** `Transform` 필드 private + 접근자, Actor `setLocal*`.
   쓰기 지점을 전부 세터로 교체. 동작 변경 0.
2. **`Component::localBounds` 추가 + 픽 일반화.** `pickActor`가 종류 분기 없이 모든 액터의
   `localBounds`를 질의. 메시는 그대로, 라이트(Point/Spot)·오디오·카메라가 바운드를 알림.
   여기서 라이트가 뷰포트에서 **클릭 선택**됩니다.
3. **아이콘 픽 + 최소 아이콘 렌더.** 바운드 없는 엔티티(Directional 라이트 등)를 아이콘
   원판으로 그리고 화면 원판 판정으로 픽. Directional 라이트 선택 가능.
4. **`Component::drawEditorVisual` + 와이어 영향 범위.** 라이트 range 구/spot 원뿔/방향,
   카메라 절두체, 오디오 반경을 라인으로. 선택 시 표시.
5. **액터 바운드 집약 + 프레이밍.** F 키로 선택 대상에 카메라 맞춤. 종류 무관.
6. **3D UI 패널 엔티티.** 얇은 판 바운드 + 패널 컴포넌트. VR 월드 UI의 토대.

1~2단계만으로 "라이트를 뷰포트에서 잡는다"는 핵심 불편이 사라집니다. 3~6은 증분입니다.

## 9. 사용자 결정이 필요한 항목

> **[해결됨 · 2026-08-26]** D1 ~ D4 는 모두 권고안대로 정했습니다. 결정과 구현 결과는 10절에 있습니다. 아래는 결정 당시의
> 선택지 기록입니다.

### D1. 공간 훅을 어디에 두는가

- **가 (권고)** `Component` 기반 클래스에 가상 훅 `localBounds`, `drawEditorVisual`.
  기본값은 각각 false와 no-op이라 기존 컴포넌트에 영향이 없고, 필요한 것만 재정의합니다.
- 나 별도 인터페이스 `ISpatialComponent`를 만들고 컴포넌트가 상속. 명시적이지만 다중
  상속·캐스팅이 늘어 이 코드베이스의 단순한 컴포넌트 모델과 어긋납니다.

권고는 가입니다. 가장 마찰이 적고, 컴포넌트가 자기 능력만 선택적으로 재정의합니다.

### D2. 트랜스폼 캡슐화 (5절)

- 가 현행 유지(public 필드) / **나 (권고)** 지금 private 캡슐화.
권고는 나입니다. 엔티티가 늘기 전에 하는 것이 가장 싸고, 파생 캐시를 나중에 안전하게
넣을 수 있습니다.

### D3. 이번 설계의 범위

- **(A, 권고)** 1~3단계. 트랜스폼 캡슐화 + 픽 일반화 + 아이콘. "모든 엔티티를 뷰포트에서
  선택"이라는 근본 문제를 해결하고 멈춥니다.
- (B) 1~5단계. 와이어 영향 범위와 프레이밍까지.
- (C) 1~6단계. 3D UI 패널 엔티티까지 한 번에.

권고는 A입니다. 근본 문제(선택 통일)를 풀고, 시각화(4단계)와 3D UI(6단계)는 실제로 그

## 10. 구현 결과 (2026-08-26 · 1~3단계)

사용자 결정: **D1 = Component 가상 훅, D2 = 트랜스폼 지금 캡슐화, D3 = 1~3단계,
D4 = 3D UI 는 개념만.**

### 1단계 — 트랜스폼 캡슐화 (D2)

- `Transform` 필드를 private 로 돌리고 접근자·세터로만 만지게 했습니다(`Transform.hpp`).
- `Actor` 도 `transform_` 를 private 로, 읽기는 `transform()`, 쓰기는 `setLocalPosition`
  `setLocalRotation` `setLocalScale` `translateLocal` `setLocalTransform` 으로만 합니다.
- 필드를 직접 쓰던 지점 35개(에디터·물리·직렬화·기즈모·undo)를 전부 세터 경유로 교체했습니다.
  **필드 직접 접근 잔여 0건.** 동작 변경은 없습니다.
- 이제 나중에 월드 바운드 캐시 같은 파생값을 되살려도, 세터가 무효화의 단일 통로라 stale 이
  재발하지 않습니다(P1 충족).

### 2단계 — 픽 일반화

- `Component::localBounds(min, max)` 가상 훅을 추가했습니다. 기본값은 false 입니다.
- `StaticMeshComponent` 가 메시 AABB 로 재정의합니다.
- `pickActor` 가 컴포넌트 종류를 분기하지 않고, 각 컴포넌트의 `localBounds` 합집합에
  광선-OBB 판정을 합니다. 메시·3D UI 패널처럼 솔리드 몸체가 있는 것이 여기서 잡힙니다.

### 3단계 — 아이콘 (라이트·카메라·오디오 선택 가능)

- `Component::editorIcon(color)` 가상 훅을 추가했습니다. Light(노랑)·Camera(파랑)·
  Audio(초록)가 재정의합니다.
- 오버레이를 합쳤습니다. 기즈모가 렌더러에 직접 그리지 않고 리스트에 덧붙이도록 바꿔서,
  에디터가 기즈모 + 아이콘을 한 리스트에 모아 한 번에 설정합니다.
- `buildEditorIcons` 가 아이콘 액터마다 카메라를 향하는 빌보드 사각형을 화면 고정 크기로
  그립니다. 선택 시 테두리를 강조합니다.
- `pickActor` 가 아이콘을 **우선** 판정합니다. 작고 명시적인 타깃이므로 솔리드 바운드보다
  먼저 화면 원판으로 잡습니다. 이제 라이트·카메라·오디오를 뷰포트에서 클릭 선택합니다.

  `drawEditorVisual` 훅은 아직 없습니다(1 ~ 3단계에서는 `localBounds` · `editorIcon` 만 넣음). 그릴 곳인 에디터 라인 ·
  삼각형 오버레이 목록은 있으므로, 4단계를 할 때 훅을 추가해 그 목록에 덧붙입니다(2026-10-15 정정).
