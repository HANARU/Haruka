## 현재 스레드 인벤토리

| 스레드 | 생성 주체 | 역할 | 엔진 데이터 접근 |
|---|---|---|---|
| 메인 | OS | 입력→틱→에디터→렌더 전체 | 전부 (소유자) |
| 셰이더 워처 | HotReloader | .spv 변경 감시 | `pending_` atomic + std::cout만 |
| Jolt 워커 ×N | PhysicsSystem (JobSystemThreadPool) | 물리 스텝 내부 병렬화 | 없음 (Update() 내부에서 join) |
| 오디오 | miniaudio (ma_engine) | 디바이스 콜백 믹싱 | 없음 (ma_* API 내부 동기화) |

## 규칙

1. **엔진 데이터는 메인 스레드 전용.**
   World / Actor / Component / HSlate 위젯 / EditorContext(로그 제외) /
   Renderer의 모든 Vulkan 객체는 메인 스레드에서만 읽고 쓴다.

2. **서브시스템 스레드는 자기 내부 데이터만 만진다.**
   서드파티(Jolt, miniaudio)의 내부 스레드가 엔진 구조체에 닿는 API를
   콜백으로 받지 않는다. 콜백이 필요하면 큐에 적재하고 메인 틱에서 소비한다.

3. **스레드 교차 통신은 두 가지 방법만 허용.**
   - `std::atomic` 플래그/카운터 (예: `HotReloader::pending_`, `EditorContext::logDirty`)
   - 뮤텍스로 보호된 큐/버퍼 (예: `EditorContext` 로그 deque)
   필드 옆 주석에 어느 뮤텍스로 보호되는지 명시한다.

4. **std::cout / std::cerr는 어느 스레드에서나 안전.**
   LogStreamBuf가 내부 락으로 직렬화한다 (2026-06-11 수정). 단, 이것이
   "백그라운드 스레드에서 UI를 만져도 된다"는 뜻이 아니다 — 로그만 예외다.

5. **블로킹 금지 구역.** 메인 루프(틱/렌더 경로)에서 파일 I/O·네트워크·join을
   새로 추가하지 않는다. 기존 위반(glTF 동기 로드)은 비동기 에셋 로딩 도입 시 해소.

## 예약된 확장 (시기 미정, 트리거 기반)

| 트리거 | 작업 |
|---|---|
| 에셋 로드 프리즈 체감 (1단계, 스레드 불필요) | **프레임 예산 기반 지연 작업 큐** — 메인 스레드에 데드라인을 준 작업 큐를 두고, 매 틱 남은 예산만큼만 소진한다. Carbon `scheduler`의 `RunTaskletsForTime` 패턴. 새 스레드를 만들지 않으므로 위 규칙 1~3과 충돌하지 않는다. |
| 에셋 로드 프리즈 체감 (2단계) | **비동기 에셋 로딩** — 워커에서 I/O+디코드, 메인에서 GPU 업로드. 첫 실전 멀티스레딩. |
| 시뮬레이션 틱 > 2~3ms | 잡 시스템 설계 착수 (프로파일 데이터 기반) |
| Quest 포팅 | OpenXR 프레임 페이싱 측정 후 게임/렌더 스레드 분리 검토 — RenderView 경계([RendererRefactor.md §4](RendererRefactor.md)) 사용 |

## 외부 대조: Carbon도 같은 규칙에 도달했습니다

이 문서의 규칙은 Haruka 내부 판단으로 세운 것이지만, Carbon Engine이 독립적으로 같은 결론에 도달했다는 사실이 실측으로 확인되었습니다.

* **상태는 정확히 한 스레드가 소유합니다.** `carbonengine/scheduler`의 `ScheduleManager::Run`은 한 번에 정확히 하나의 tasklet으로만 전환하며, GIL 아래 협조적 마이크로스레드이므로 병렬 실행이 없습니다.
* **작업은 스레드를 이동하지 않습니다.** tasklet이 스레드를 옮기려 하면 런타임 에러가 나며 문구가 `"Cannot switch tasklet from another thread"`입니다. 이는 이 문서 규칙 1과 2의 다른 표현입니다.
* **교차 상호작용은 소유자 큐에 넣는 것뿐입니다.** Channel은 버퍼 없는 랑데부이며, 수신자가 없으면 송신자가 블록합니다.
* **제약 완화안이 검토된 뒤 기각되었습니다.** scheduler의 설계 문서에 이 제약을 완화하는 안이 논의되었다가 채택되지 않은 기록이 남아 있습니다. 즉 같은 규칙을 두 프로젝트가 각자 유도했고, 한쪽은 완화를 시도했다가 되돌렸습니다.

### scheduler를 잡 시스템으로 보는 매핑은 근거가 없습니다

[Full_Carbon_Ecosystem_Analysis.md](archive/Full_Carbon_Ecosystem_Analysis.md)의 이전 판은 Carbon의 `scheduler`를 엔진 잡 시스템으로 보고 Haruka의 잡 시스템 설계에 대응시키는 제안을 담고 있었습니다. 이 매핑은 성립하지 않으며, 해당 문서는 같은 검증 과정에서 정정되어 현재는 `scheduler`를 "잡 시스템 설계 입력으로는 사용 불가"로 분류합니다. 이유는 다음과 같습니다. `scheduler`는 잡 시스템이 아니라 **CPython 3.12 C 확장 모듈 `_scheduler`**이며, Stackless Python의 Tasklet/Channel API를 greenlet 패키지 위에 재구현한 것입니다(`Tasklet.h`의 private 멤버가 `PyGreenlet* m_greenlet`이고 전환은 `PyGreenlet_Switch`입니다). 워커 스레드도, 잡 그래프도, 의존성 간선도, 작업 훔치기도, SIMD 디스패치도 없습니다. 소스는 22개 파일이고 그중 절반이 Python 바인딩 셰임입니다. 따라서 이 문서가 채택한 방식, 즉 **잡 시스템을 미리 설계하지 않고 측정된 트리거(시뮬레이션 틱 2~3ms)가 걸릴 때 착수한다**는 규칙이 옳으며, Carbon에서 잡 시스템 설계를 빌려올 수는 없습니다.

### 다만 건질 패턴이 하나 있습니다

`RunTaskletsForTime`은 **프레임 예산 기반 협조적 실행 패턴**입니다. 새 스레드를 만들지 않고, 메인 스레드의 지연 작업 큐를 주어진 데드라인까지만 소진한 뒤 나머지를 다음 프레임으로 넘깁니다. 이 문서의 규칙 1~3은 스레드 경계에 대한 것이고 이 패턴은 스레드를 늘리지 않으므로 충돌하지 않습니다. 규칙 5(블로킹 금지 구역)에도 부합합니다. 한 번에 다 하지 않고 예산만큼만 하는 것이 곧 블로킹을 피하는 방법이기 때문입니다. 그래서 위 예약된 확장 표에 비동기 에셋 로딩보다 **먼저 시도할 1단계**로 추가했습니다. 이것으로 프리즈가 충분히 완화되면 첫 실전 멀티스레딩 도입 시점을 그만큼 뒤로 미룰 수 있습니다.
