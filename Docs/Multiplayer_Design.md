# 멀티플레이 구조 설계 초안 (2026-11-24)

> **문서 지위:** 조사와 설계 **초안**입니다. 2026-11-24 에 사용자가 7절 질문에 세 차례 답했고, 그 답(0절)에 맞춰 D5 · D7 ~ D10 · D12 ~ D14 와 4 ~ 7절을
> 다시 썼습니다. D2(고정 틱 + 표시 보간)는 사용자 결정으로 구현 중입니다. 나머지 결정은 권장안이며, 세부 질문 여섯 개가 남아 있습니다(7-2). [Layer_Architecture.md](Layer_Architecture.md) 3절은 네트워크 계층(HNet)을 "범위 밖"으로 판정해 두었고, 이 문서는 그 판정을
> 바꾸지 않습니다. 판정을 바꿀 때 무엇을 정해야 하는지, 그리고 **싱글만 만드는 동안에도 지금 지켜 두면 나중의 재작성을 막는 규칙**(3절)이
> 무엇인지를 정리합니다.

사용자 의도(2026-11-23)는 싱글 전용과 멀티플레이 포함을 **하나의 체계로 통합**하는 것입니다. 지금 구조를 정해 두어야 앞으로 추가할 기능의
복잡도가 낮아진다는 판단입니다. 형식은 [Save_And_Settings.md](Save_And_Settings.md)처럼 "조사 → 결정 → 단계"의 순서를 따릅니다.

### 1-2. 다른 엔진 (2026-11 기준, 출처는 8절)

| 주제 | Unreal(5.8 정식 · 5.9 미리보기) | Unity(NGO 3.2 · Unity Netcode 7.2) | Godot(4.7) |
|---|---|---|---|
| 싱글과 멀티의 관계 | NetMode 넷(Standalone · DedicatedServer · ListenServer · Client). Standalone 을 "서버 기능을 모두 가지므로 여전히 서버"로 보고, 멀티용으로 쓴 게임플레이가 싱글에서 그대로 돈다고 적습니다 [U1] | NGO 는 `SinglePlayerTransport` + `StartHost()` 로 네트워크 코드를 고치지 않고 싱글을 돌립니다 [N12]. Unity Netcode 는 서버 월드와 클라이언트 월드를 나누고, 한 프로세스 호스트는 "이중 월드" 또는 "단일 월드 호스트"(새 프로젝트 기본값)입니다. 단일 월드는 가볍지만 전용 서버와 코드 길이 달라 동작이 갈릴 수 있다고 경고합니다 [E7] | 모든 노드가 `multiplayer` 를 갖고, 권위는 기본이 서버(피어 1)입니다 [G2] |
| 권위 질의 | 액터 Role(Authority · AutonomousProxy · SimulatedProxy). **복제하지 않는 액터는 클라이언트에서도 Authority** 로 보이므로 `HasAuthority()` 는 "서버인가"와 같지 않습니다 [U2] | 서버가 최종 권위, 소유자는 소유자 권위로 정한 기능만. 분산 권위 모드는 "정확한 예측이 필요한 경쟁 게임에는 맞지 않고 부정행위가 쉽다"고 적습니다 [N8][N9] | `set_multiplayer_authority` 로 노드마다 바꿉니다 [G2] |

### 1-3. VR 쪽 도구와 플랫폼

- **Meta Quest 플랫폼:** 전송 · 매치메이킹 · 음성을 주지 않습니다. Rooms · Matchmaking · P2P · VoIP 는 2023년 3 ~ 4월에 폐기되었고(폐기 뒤 만든 앱은
  쓸 수 없음), Meta 는 대안으로 Photon · Epic · PlayFab · Unity 를 안내합니다 [M1][M2][M3]. 남은 것은 사람을 모으는 기능(Destinations ·
  Group Presence · 초대 · Roster)이고 네이티브 C API 로 쓸 수 있습니다 [M4][M5]. 참가 의도(딥링크)의 세션 ID 를 앱이 자기 방 ID 에 대응시켜야 합니다.
  스토어 요건으로 멀티플레이 앱은 사용자 신고 수단이 필수이고(VRC.Content.3), 혼합 연령 앱은 나이 범주 API 호출이 필수입니다 [M6][M7].
  일시정지 요건(VRC.Quest.Functional.2, 필수)의 문장은 "싱글 플레이 앱은 Horizon OS 가 요청하면 멈춰야 한다"이며 멀티 세션을 대상으로 적지 않습니다 [M10].
  Meta Avatars SDK 는 기능 종료 상태이고 Unity 전용이라 아바타는 직접 만들어야 합니다 [M8].
- **Normcore:** 운영 중이지만 문서상 Unity 전용입니다(자체 엔진에서 쓸 길은 찾지 못함, 확신 낮음). 소유권 모델은 참고할 만합니다: 쥘 때 소유권을 요청하고
  쥔 동안 키네마틱으로 손을 따라가게 하며, 내 물체가 주인 없는 물체와 부딪히면 그 물체의 소유권도 요청하고, 잠들면 소유권을 비웁니다. 전송 기본값은 20 Hz 입니다 [NC1][NC2][NC3].
- **Photon:** Fusion 2 는 Unity 전용입니다. 엔진과 무관한 C++ SDK 로 Realtime Core 6(방 · 매치메이킹 · 이벤트 중계, C++20)과 Fusion Core 3
  ("Fusion 3 의 핵심인 엔진 무관 C++ 네트워킹 SDK")이 나왔습니다 [P1][P2]. Fusion Core 는 릴리스 노트의 모든 빌드가 미리보기이고 내려받기가 문의
  방식이라는 조사 결과가 있습니다(확신 낮음). 요금은 동시 접속자 수 기준입니다 [P6].
- **VR 샘플의 공통 방식(Fusion VR Shared · VR Host 샘플 [P3][P4], 직접 확인은 요약본 기준):**
  - 자기 머리 · 손은 네트워크 상태를 기다리지 않고 그리기 직전에 최신 추적 값으로 덮어씁니다.
  - 호스트 권위 샘플에서도 리그 자세는 입력에 실어 보내는 절대값이고, 순간 이동도 로컬에서 먼저 실행합니다.
  - 쥐기는 쥐는 사람에게 권위를 넘기는 방식이며, 권위를 기다리는 동안 손을 따라 그립니다. 쥐기 감지는 재시뮬레이션 틱에서 하지 않습니다.
  - Meta Building Blocks · VRChat 도 쥘 때 소유권을 넘깁니다 [M9][V1].
- **Glenn Fiedler "Networked Physics in Virtual Reality"(2018-02-22, Oculus 후원) [GF4]:** VR 손으로 물체를 쥐고 던지는 협동 샘플의 설계 기록이고,
  공개 자료 중 가장 구체적입니다. 결정론 lockstep 은 물리가 결정적이지 않아 제외했고, 90 Hz 에서 지연 250 ms 를 예측으로 숨기려면 그리는 프레임마다
  물리를 약 25 스텝 돌려야 해 비현실적이라고 판단했습니다. 전용 서버는 비경쟁 샘플에 운영비를 들일 까닭이 없어 택하지 않았습니다. 택한 방식은
  **권위(건드린 사람)와 소유(쥔 사람)를 나눈 분산 권위**입니다. 물체마다 권위 순번과 소유 순번을 두어 소유가 권위를 이기고, 모든 패킷이 호스트를 지나며
  호스트가 중재합니다. 아바타 패킷은 100 ms 지터 버퍼로 보간합니다. 글의 결론은 "협동 경험에만 맞고 서버 권위의 보안은 주지 못한다"입니다.
- **복제 빈도와 손가락:** 공개 수치는 10 ~ 30 Hz 대입니다(Normcore 20 Hz, Fusion 2.0 Shared 틱 32 · 전송 16, Fusion Core 권위 전송 30 Hz) [NC1][P5][P2].
  손 추적 관절은 회전 24개를 관절별 가동 범위로 압축해 한 손 18 ~ 19 바이트로 줄인 사례가 있습니다 [P7]. 컨트롤러 기반 손 모양은 입력 값 몇 개만 보내고
  받는 쪽이 다시 만듭니다 [P3].
- **음성:** libopus 1.6.1 이 최신입니다 [A1]. 기성 SDK 중 자체 엔진 · Android 에서 쓸 수 있다고 확인된 것은 Vivox Core(Android arm64 지원 목록)와
  EOS Voice(로비 연동, Android 지원은 확신 낮음)입니다 [A2][B2]. Photon Voice 는 Unity 용만 확인했습니다. 직접 만들 때의 구성은 마이크 수집 →
  반향 제거 · 잡음 억제 → Opus → 비신뢰 전송 → 화자별 지터 버퍼 → 3D 음원입니다 [NC4].

### 1-6. 결정론 lockstep 대 상태 복제

- **Jolt 는 플랫폼 사이 결정론을 옵션으로 지원합니다.** 기본 조건은 "같은 순서의 API 호출 + 같은 바이너리"이고, CMake 옵션
  `CROSS_PLATFORM_DETERMINISTIC` 을 켜면 약 8% 느려지는 대신 컴파일러 · OS · 아키텍처(x86 · ARM 등)가 달라도 같은 결과가 난다고 적습니다.
  다만 같은 절이 "다른 기능보다 덜 시험되었다"고 적고, 매 빌드 검증하는 구성 목록에 Windows x64 와 Linux · macOS ARM64 는 있지만 **Android 는 없습니다** [J1].
- **결정론은 물리 라이브러리만의 일이 아닙니다.** 같은 절이 응용 프로그램에 요구하는 것은 부동소수점 정밀 모드, 곱셈 · 덧셈 융합 끄기, FPU 상태 일치,
  표준 삼각함수 · `std::sort` · `std::hash` 대신 Jolt 의 것을 쓰기입니다. 넓은 단계 질의와 접촉 콜백의 순서는 결정적이지 않아 모아서 정렬해야 합니다 [J1].
  Godot 의 Jolt 통합은 "Jolt 자체는 결정적이지만 Godot Jolt 는 그런 보증을 할 수 없다"고 적습니다 [J2].
- **방식별 차이(Gaffer On Games 연재) [GF1][GF2][GF3]:** lockstep 은 입력만 보내 대역폭이 작지만 비트 단위 일치가 필요하고 입력 지연 또는 롤백 비용을
  치릅니다. 상태 복제는 결정론이 필요 없고 인원을 늘리기 쉽지만 대역폭이 크고 보간 지연이 생깁니다.
- **서버 권위에서의 예측과 지연 보정(2026-11-24 추가, Gabriel Gambetta 의 연재) [LC1][LC2]:** 클라이언트는 입력마다 순번을 붙여 보내고, 서버는 마지막으로 처리한 순번을
  상태와 함께 돌려줍니다. 클라이언트는 받은 상태에서 출발해 아직 처리되지 않은 입력을 다시 적용합니다. 판정의 지연 보정은 서버가 시각이 붙은 입력으로 과거의 한 순간을
  다시 구성해 "쏜 순간 조준선에 무엇이 있었는가"를 보는 것이고, 맞는 쪽이 엄폐한 직후에 맞을 수 있다는 값을 치릅니다.

### 1-7. 공통 구조

1. **싱글은 "접속자가 없는 서버"입니다.** UE · Unity 가 모두 공식으로 이 길을 제공합니다. 게임 코드는 "내가 권위인가"만 묻고 실행 모드를 모릅니다.
2. **시뮬레이션은 고정 틱, 화면은 보간입니다.** 예측이 있든 없든 서버와 클라이언트가 같은 틱 번호를 공유합니다.
3. **배치된 객체는 파일의 안정된 이름(경로 · 해시 · GUID)으로, 실행 중 만든 객체는 권위가 준 ID + 등록된 원본(프리팹)으로** 대응시킵니다.
4. **복제할 값은 저장할 값과 따로 선언합니다.** 조건(소유자만 · 처음만)과 전달 방식(바뀔 때 신뢰 · 매번 비신뢰)이 값마다 붙습니다.
5. **VR 에서는 자기 머리 · 손을 서버가 고치지 않고, 쥔 물체는 쥔 사람이 권위를 가집니다.** 범용 물리 예측(되감기)은 UE · Unity 에서도 실험 단계이거나 비용 경고가 붙어 있습니다.
   앞 문장의 "쥔 사람이 권위"는 협동용 샘플과 서비스에서 본 공통점입니다. 공개 대전에 맞춘 판단은 D7 · D12 에 따로 적었습니다.
6. **플랫폼은 사람을 모으는 일(신원 · 초대 · 프레즌스)만 하고, 전송 · 방 · 음성은 앱의 몫입니다.**

### D1 실행 모드와 권위 API

| 선택지 | 내용 |
|---|---|
| 가 | 지금처럼 싱글 코드만 쓰고, 멀티는 나중에 따로 붙입니다 |
| **나(권장)** | 월드마다 실행 모드(`Standalone` · `ListenServer` · `DedicatedServer` · `Client`)를 두고, 싱글은 접속자 없는 서버로 같은 코드 길을 지납니다(UE NetMode). 한 프로세스에 월드는 하나입니다 |
| 다 | 싱글도 서버 월드와 클라이언트 월드를 둘 다 띄우고 프로세스 안 연결로 잇습니다(Unity Netcode 이중 월드) |

- **권장안:** 나. 게임 코드에 여는 질의는 넷입니다.
  - `world.isServer()`: 이 월드가 권위 시뮬레이션을 도는가(Standalone · ListenServer · DedicatedServer 에서 참).
  - `actor.hasAuthority()`: 이 액터의 상태를 여기서 바꿔도 되는가. 서버에서는 참이고, 클라이언트에서는 복제하지 않는 로컬 액터만 참입니다. No Trust 전제(0절)에서
    복제되는 액터의 권위는 클라이언트로 넘어가지 않습니다(초안의 "권위를 넘겨받은 액터"는 철회).
  - `actor.netRole()`: `Authority`(서버) · `Predicted`(이 기기의 플레이어가 조종해 앞서 계산하는 것, D7) · `Remote`(서버 값을 보간해 그리는 것). UE 의 Authority ·
    AutonomousProxy · SimulatedProxy 와 같은 구분입니다(2026-11-24 추가: 예측이 필요해져 "권위는 아니지만 내 것"을 가릴 질의가 필요함).
  - `actor.ownerPlayer()` · `world.localPlayers()`: 누구의 것인가, 이 기기의 플레이어는 누구인가.
- **근거:** UE · Unity 가 같은 구조를 공식으로 제공합니다(1-2). "다"는 전용 서버와 같은 코드 길을 지나는 장점이 있지만 Quest 에서 월드 둘과 로컬 직렬화 비용을
  치릅니다. Unity 도 새 프로젝트 기본값을 단일 월드로 두었습니다 [E7]. 단일 월드의 약점(전용 서버와 동작이 갈릴 수 있음)은 화면 없는 두 프로세스를
  붙이는 자동 시험(6절 N1)으로 막습니다. UE 의 함정(복제하지 않는 액터는 클라이언트에서도 권위)을 피하려고 "서버인가"와 "권위인가"를 다른 질의로 나눕니다.
- **비용:** `src/scene`(World · Actor)에 열거형 둘과 질의 넷. 네트워크가 없는 동안은 상수를 돌려주므로 동작이 바뀌지 않습니다. 작습니다.
- **운영 형태와의 관계:** 실제 운영은 전용 서버(D9)입니다. `ListenServer` 는 개발 · 시험용으로만 남기고, `Standalone` 은 싱글 플레이가 지나는 길로 그대로 씁니다.
- **실행 모드가 정하는 기본값(2026-11-24 사용자 답 17):** 헤드셋을 벗거나 시스템 메뉴를 열어 초점을 잃었을 때의 동작은 실행 모드마다 기본값이 다릅니다.
  `Standalone` 은 OS 가 요청하면 멈추고(Meta 스토어의 싱글 플레이 요건 [M10]), 멀티 세션의 `Client` 는 멈추지 않습니다(월드가 서버의 것이므로). 두 기본값 모두 게임 설정으로
  바꿀 수 있고, 멀티에서 "멈춤"의 뜻은 D9 에 적었습니다. 싱글의 "멈추지 않음" 설정은 Quest 판에도 열어 두되 기본값은 "멈춤"입니다(사용자 답 36, 심사 위험은 D9).
  지금은 게임 실행 파일의 정책 값 하나(`pauseOnXrFocusLoss`, `Engine.cpp` 1034 ~ 1047행)가 모드와 무관하게 정합니다.
- **정해야 하는 때:** **지금.** API 가 있어야 3절의 규칙을 코드로 지킬 수 있습니다.

### D2 시뮬레이션 틱과 표시 보간

| 선택지 | 내용 |
|---|---|
| 가 | 지금 그대로: 게임 틱은 가변 dt, 물리 스텝은 헤드셋 주사율 |
| **나(권장)** | 프로젝트가 정한 고정 시뮬레이션 틱 + 모든 액터의 표시 보간. 로컬 머리 · 손과 손에 쥔 물체는 보간하지 않고 그리기 직전의 추적 값으로 그립니다 |
| 다 | 고정 틱 + 프레임 끝의 남는 시간만큼 임시로 더 진행했다가 되돌리기(Unity Netcode 의 부분 틱). 표시 지연이 없지만 되감기 장치가 필요합니다 |

- **권장안:** 나. 구조는 다음과 같습니다.
  1. `Engine::tickFrame` 이 누적기로 0번 이상 시뮬레이션 틱을 돌립니다. 틱 한 번은 "틱 입력 확정 → `World::tick(틱 길이)` → 게임 `onTick` → 물리 스텝 1회 →
     `tickPostPhysics`"입니다. 물리의 누적기(`PhysicsSystem.cpp` 929 ~ 967행)는 엔진 쪽으로 올라갑니다.
  2. 프레임마다 한 번 도는 **표시 단계**를 따로 둡니다. 애니메이션 섞기 · 파티클 · UI · 소리처럼 시뮬레이션 상태를 바꾸지 않는 일이 여기서 프레임 dt 로 돕니다.
  3. 보간은 Transform 에 쓰지 않고 **렌더 추출 단계**(`components/RenderExtract`, [Engine_Structure_Design.md](Engine_Structure_Design.md) 12절)가 이전 틱 · 지금 틱 자세를 섞어
     렌더 입력에만 넣습니다. 추출이 이미 한 곳에 모여 있어 고칠 자리가 좁습니다. `RigidBodyComponent::interpolate` 와 그 상태 필드는 이 공통 장치로 대체됩니다.
  4. `XrSessionController.cpp` 150 ~ 155행의 "물리 스텝을 헤드셋 주사율에 맞춤"은 없앱니다.
  5. 입력은 프레임 여러 개의 값을 틱 하나의 입력으로 합칩니다(눌림 · 뗌이 틱 사이에서 사라지지 않게). UE Mover 문서가 고정 틱의 함정으로 같은 점을 듭니다.
- **근거:** 스텝 길이가 기기마다 다르면(C3) 서버 한 대가 여러 헤드셋과 같은 시뮬레이션을 돌릴 수 없고, 가변 dt 게임 틱(C1)은 서버 대조 · 재실행을 막습니다.
  싱글에서도 이득이 있습니다. 물체의 움직임(쌓기 · 관절 · 던지기)이 72 Hz · 90 Hz · 144 Hz 기기에서 같아지고, 시험이 주사율과 무관해집니다.
  "다"는 표시 지연이 없지만 되감기 장치 전체가 필요합니다(D7 에서 채택하지 않음).
- **VR 에서 조심할 점:** 보간은 화면을 최대 한 틱만큼 늦춥니다. 머리 · 손이 늦으면 멀미가 나므로 로컬 리그는 예외로 둡니다(지금도 `TrackedPoseComponent` 가
  프레임마다 추적 값을 씁니다). 손에 쥔 물체가 손보다 한 틱 늦게 따라오면 눈에 띄므로, 표시 단계에서 손 자세에 붙여 그립니다(Fusion VR 샘플의 방식).
  이 부분은 헤드셋으로 확인해야 합니다.
- **틱 값:** 후보는 60 · 72 · 90 Hz 입니다. 서버 비용과 Quest CPU 를 재서 정합니다(7절 질문 11). 싱글과 멀티가 같은 값을 써야 "하나의 체계"가 됩니다.
- **비용(추정):** `runtime/Engine.cpp`(틱 루프 · 표시 단계), `physics/PhysicsSystem`(누적기 · 보간 제거, 틱당 스텝), `scene`(액터의 이전 틱 자세 보관, 틱 그룹에
  "표시" 추가), `components/RenderExtract`(보간), `input/HInputSystem`(틱 입력 합치기), `runtime/XrSessionController`(스텝 맞춤 제거), 틱을 가진 컴포넌트 7개(C5)의
  분류, 시험(`--fixed-dt` 를 틱 길이와 맞추면 기준 PNG 는 프레임과 틱이 1 : 1 로 유지됨, 다시 재야 할 수 있음). 빌드 2 ~ 3회 크기의 묶음 3 ~ 4개와 헤드셋 확인 1회로 봅니다.
- **정해야 하는 때:** **게임플레이 코드를 더 쌓기 전.** 틱을 가진 컴포넌트가 7개뿐인 지금이 가장 쌉니다. 결정 항목 가운데 미룰수록 비용이 가장 빨리 느는 항목입니다.
- **구현 뒤 이어서 할 것(2026-11-24 추가):** 사용자가 "지금 넣자"고 정해 구현을 시작했고, 틱 기본값은 60 Hz 로 시작합니다(헤드셋에서의 60 · 72 · 90 Hz 비교는 나중).
  위 구조는 그대로 두고, 대전 · No Trust · 전용 서버 때문에 이 구조 위에 더 필요한 것만 적습니다. 모두 네트워크 준비(4절 P3 · P5)나 네트워크 구현 때의 일입니다.
  1. **틱 번호.** 월드가 0 에서 시작해 틱마다 1 씩 느는 번호를 갖고, 게임 시간과 타이머가 그 번호에서 나오게 합니다. 서버와 클라이언트가 "몇 번 틱의 입력 · 상태인가"로
     서로를 맞춥니다(D7 의 입력 순번, D14 의 "내가 보던 틱").
  2. **틱 입력 묶음.** 눌림 · 뗌 보존 위에, 플레이어마다 한 틱의 입력(축 · 동작 · 머리와 손 자세 · 손가락 · 쥐기 의도)을 틱 번호와 함께 값 하나로 묶습니다. 이 묶음을 보내고,
     서버는 틱 번호마다 하나만 쓰며, 클라이언트는 서버가 처리했다고 알리기 전까지 보관합니다.
  3. **한 액터만 다시 실행하기.** 자기 이동의 보정은 그 캐릭터의 이동 함수만 여러 번 다시 부릅니다. 월드 전체 틱과 따로 부를 수 있는 모양이어야 합니다(P5).
  4. **밀린 틱의 처리.** 프레임당 틱 수 상한으로 시간을 버리는 처리는 싱글에서는 "게임이 느려짐"으로 끝나지만, 클라이언트는 서버의 틱 번호를 따라가야 합니다.
     멀티 세션의 클라이언트에서는 버리는 대신 서버 상태로 건너뛰는 정책이 따로 필요합니다.
  5. **서버 시계에 맞추기.** 클라이언트는 입력이 제때 닿도록 서버보다 조금 앞선 틱을 돌고, 누적기에 들어가는 시간을 조금 늘리거나 줄여 그 간격을 유지합니다
     (UE · Unity 가 같은 방식, 1-2). 원격 액터의 표시 보간은 로컬 틱이 아니라 받은 상태의 시간축(지터 버퍼)을 씁니다.
  6. **시간 배율과 일시정지.** 멀티 세션에서는 서버만 바꿀 수 있습니다(D9 의 방 규칙).
  7. **환경 사이 비교.** 프레임 빈도와 무관함을 확인하는 물체 자세 비교를 Windows · Linux · Quest 사이의 비교로 넓힙니다(6절 V3).

### D3 네트워크 ID 와 실행 중 생성

| 선택지 | 내용 |
|---|---|
| **가(권장)** | 액터 GUID(64비트)를 네트워크 정체성으로 그대로 씁니다. 실행 중 생성은 권위만 하고, 권위가 정한 GUID 를 생성 알림에 실어 보냅니다. 패킷에는 세션 안의 짧은 번호를 씁니다 |
| 나 | 네트워크 전용 ID 를 따로 둡니다(UE NetGUID 의 정적 · 동적 구분) |
| 다 | 이름 경로로 대응시킵니다(Godot) |

- **권장안:** 가. 씬에 배치된 액터는 서버와 클라이언트가 같은 씬 파일을 `Keep` 정책으로 읽으므로 이미 GUID 가 같습니다. 접속할 때 씬 · 묶음 파일의 해시를
  비교해 같은 콘텐츠인지 확인합니다. 실행 중 생성은 "프리팹 논리 경로 + 권위가 정한 GUID 목록 + 처음 상태"로 알립니다. 지금 GUID 정책 둘(`Keep` · `Fresh`)에
  "권위가 준 값을 그대로 넣음"을 하나 더합니다(`sceneio/GuidRemap`). 연출용 로컬 액터는 복제하지 않고 지금처럼 만듭니다.
- **근거:** 세 엔진이 모두 "배치된 것은 파일의 안정된 이름, 생성된 것은 권위가 준 ID + 등록된 원본"입니다(1-7). Haruka 는 저장 게임과 액터 참조가 이미 GUID 를
  쓰므로([Save_And_Settings.md](Save_And_Settings.md) D3) ID 체계를 하나로 유지할 수 있습니다. 기존 샘플 씬에 `GUID:` 줄이 없는 것([Object_References.md](Object_References.md) "남긴 것")은
  멀티 전에 저장해 고정해야 합니다.
- **No Trust 보충(2026-11-24):** 클라이언트는 복제 대상 액터를 만들거나 지울 수 없고 서버에 요청만 합니다. 콘텐츠 해시 비교는 판이 맞는지 보는 호환 확인이며,
  클라이언트가 해시를 속일 수 있으므로 부정행위 방지 수단으로 쓰지 않습니다. 해시는 **시뮬레이션에 쓰는 콘텐츠**(씬 · 프리팹 · 충돌 메시 · 물리 설정)만으로 만듭니다.
  텍스처 압축처럼 판마다 다른 표시용 콘텐츠를 넣으면 Quest 판과 PC 판의 해시가 달라져 나중에 크로스플레이를 켤 수 없습니다(D10).
- **비용:** GUID 정책 하나, 생성 통로에 "복제 대상인가" 표시, 접속 때 콘텐츠 해시 확인. 작습니다.
- **정해야 하는 때:** 네트워크 구현 때. 다만 "게임플레이 액터는 프리팹 경로로, 한 통로에서 만든다"는 규칙은 지금부터 지킵니다(3절 R4).

### D4 복제 선언 방식

| 선택지 | 내용 |
|---|---|
| 가 | 씬 파일용 `writeFields` · `readField` 를 그대로 복제에 씁니다(쓰는 쪽만 이진으로 바꿈) |
| **나(권장)** | 컴포넌트에 복제 상태 방문 함수를 하나 더 둡니다. 방문자 하나가 쓰기 · 읽기 · 바뀜 비교를 모두 하고, 값마다 양자화와 조건을 적습니다 |
| 다 | 디테일 패널용 `buildProps` 의 칸에 복제 표시를 붙입니다 |

- **권장안:** 나. 모양은 `writeFields` 와 같은 방문자입니다(예: `netState(v)` 안에서 `v.f(health)` · `v.ref(target, OwnerOnly)`). 같은 방문자를 세 곳에 씁니다:
  틱마다의 바뀐 값 전송, 늦게 들어온 사람에게 주는 전체 상태, 그리고 [Save_And_Settings.md](Save_And_Settings.md)가 남겨 둔 "액터 상태 자동 스냅숏". Transform 과 강체 상태(위치 · 회전 ·
  속도 · 잠듦)는 엔진이 직접 복제합니다. 바뀜 감지는 처음에는 틱 끝에 이전 값과 비교하는 방식으로 충분합니다(UE 기본 방식). 통지 방식(Iris)은 수가 늘면 봅니다.
- **근거:** 저장할 값과 복제할 값은 다릅니다. 씬 파일의 값은 설계 때 정한 설정(이동 속도 · 질량)이고, 복제할 값은 실행 중 상태(체력 · 문이 열렸는가)입니다.
  세 엔진 모두 둘을 따로 선언합니다(1-7). `buildProps` 는 `std::function` 게터 · 세터와 칸 이름으로 값을 찾는 에디터용 구조라 초당 수십 번 도는 길에 맞지 않습니다.
- **No Trust 보충(2026-11-24):** 같은 방문자를 예측 상태의 보관과 되돌리기(D7 의 자기 이동)에도 씁니다. 값마다 붙는 조건(소유자에게만 보냄 등)은 대역폭뿐 아니라
  정보 은닉에도 쓰입니다. 보내지 않은 값은 조작한 클라이언트도 볼 수 없습니다.
- **비용:** `src/scene` 에 방문자 인터페이스(작음) + 복제할 컴포넌트마다 함수 하나. 컴포넌트 수에 비례합니다.
- **정해야 하는 때:** 네트워크 구현 때. 지금은 "실행 중 상태를 컴포넌트의 평범한 멤버로 둔다"만 지킵니다(3절 R6).

### D5 동기화 모델

| 선택지 | 내용 |
|---|---|
| 가 | 결정론 lockstep 또는 롤백(입력만 보냄) |
| **나(확정)** | 서버 권위 + 상태 복제. 클라이언트는 자기 것만 앞서 계산하고(예측) 서버 결과로 바로잡습니다(D7 · D12) |
| 다 | 분산 권위(만든 사람 · 건드린 사람이 시뮬레이션, 서버는 중계만) |

- **결론:** 나. 공개 매치 No Trust(0절)라는 전제에서 남는 선택지는 이것뿐입니다.
- **"가"를 택하지 않는 까닭:** Jolt 때문이 아닙니다. Jolt 는 x86 과 ARM 사이 결정론을 옵션으로 지원합니다(약 8% 비용, Android 는 매 빌드 검증 목록에 없음, 1-6).
  걸리는 것은 그 밖의 전부입니다. 컴포넌트 틱 · 손 쥐기 풀이 · 애니메이션 · 길 찾기의 모든 계산이 두 아키텍처에서 비트 단위로 같아야 하고, 물리 콜백 순서를
  정렬해야 하며, Godot 의 Jolt 통합은 그 보증을 포기했습니다. VR 의 머리 · 손은 입력 지연을 둘 수 없고, 늦게 들어오는 사람을 받기 어렵습니다. 대전에서는
  모든 클라이언트가 월드 전체 상태를 갖게 되어 상대의 위치를 숨길 수 없다는 약점도 더해집니다.
- **"다"를 택하지 않는 까닭:** 클라이언트가 상태를 정하는 구조이므로 공개 매치에 쓸 수 없습니다. Unity 문서는 분산 권위가 "부정행위가 쉽다"고 적고 [N9],
  Fiedler 의 VR 물리 글도 자신의 분산 권위 방식이 "협동 경험에만 맞고 서버 권위의 보안은 주지 못한다"고 결론짓습니다 [GF4]. 초안이 협동을 전제로 권장했던
  "자기 리그와 쥔 물체만 그 플레이어의 권위"는 이 답으로 철회합니다.
- **Jolt 결정론 옵션의 쓸모가 커졌습니다.** 서버는 Linux x64, 클라이언트는 Windows x64 와 Quest arm64 입니다. 클라이언트가 앞서 계산한 결과(쥔 물체 · 던진 물체)가
  서버와 같게 나올수록 바로잡는 일이 줄어듭니다. 세 환경에서 같은 장면을 돌려 비교하는 실험을 이른 확인 항목으로 둡니다(6절 V3). 옵션을 켜더라도 lockstep 을
  하려는 것이 아니라 예측이 잘 맞게 하려는 것입니다.
- **비용:** 방향만 정하는 항목입니다.
- **정해야 하는 때:** 정해졌습니다(2026-11-24 사용자 답). Jolt 옵션은 V3 실험 뒤에 정합니다.

### D6 원격 호출(RPC)

| 선택지 | 내용 |
|---|---|
| 가 | 함수 단위 RPC(UE 의 Server · Client · NetMulticast). C++ 에 코드 생성기나 매크로 체계가 필요합니다 |
| **나(권장)** | 메시지 구조체 단위. 지금 있는 형 기반 이벤트 버스(`World::events()`, [Gameplay_Tools.md](Gameplay_Tools.md) D4)에 "어디로 보낼지"를 더합니다 |
| 다 | 원격 호출을 두지 않고 복제 상태만 씁니다 |

- **권장안:** 나. 메시지 형을 등록하고(직렬화 함수 포함) `Server` · `Owner` · `Everyone` · `NotOwner` 같은 대상을 정해 보냅니다(Unity `SendTo` 와 같은 구분).
  싱글에서는 지금의 `publish` 처럼 바로 부릅니다. 클라이언트에서 서버로 가는 메시지는 "요청"이고 서버가 검증한 뒤 상태를 바꿉니다. 전달은 신뢰가 기본이고,
  연출처럼 잃어도 되는 것만 비신뢰로 적습니다.
- **근거:** Haruka 에는 리플렉션 코드 생성기가 없으므로 함수 단위 RPC 는 새 도구가 필요합니다. 구조체 메시지는 템플릿만으로 됩니다. 이벤트 버스를 넓히면
  싱글 코드와 멀티 코드가 같은 API 를 씁니다. 지속되는 상태를 메시지로 보내면 늦게 들어온 사람이 받지 못하므로, 상태는 D4, 일회성 사건은 D6 로 나눕니다.
- **No Trust 보충(2026-11-24):** 클라이언트에서 서버로 가는 메시지는 형마다 검증 함수와 빈도 한도를 함께 등록해야 보낼 수 있게 합니다. 메시지에는 "무엇을 하고 싶다"만
  싣고 결과(위치 · 속도 · 피해량)는 싣지 않습니다(3절 R12). 월드 상태를 바꾸는 것은 서버에서 클라이언트로 가는 방향뿐입니다.
- **비용:** `scene/EventBus` 에 대상과 직렬화 등록(중간). 네트워크 모듈이 운반합니다.
- **정해야 하는 때:** 네트워크 구현 때.

### D7 클라이언트 예측 범위

| 선택지 | 내용 |
|---|---|
| 가 | 예측 없음. 자기 것도 서버 상태를 보간해 그립니다 |
| 나 | 물리 월드 전체를 예측하고 되감아 다시 시뮬레이션합니다(UE Chaos 재시뮬레이션, Unity Netcode 물리 예측) |
| 다 | 되감기 없이 권위를 나눕니다(자기 리그와 쥔 물체는 클라이언트가 정함). **초안의 권장안이었으나 No Trust 에서는 쓸 수 없어 철회합니다** |
| **라(권장)** | 서버가 모든 것을 정하고, 클라이언트는 **범위를 좁혀** 예측합니다. 자기 이동만 "예측 + 서버 대조 + 입력 재실행"을 하고, 추적 자세는 입력으로 보내 서버가 타당성을 검사합니다. 물리 월드 전체는 되감지 않습니다 |

- **권장안:** 라. 대상별로 다음과 같이 나눕니다.

| 대상 | 클라이언트가 하는 일 | 서버가 하는 일 | 어긋났을 때 |
|---|---|---|---|
| 자기 이동(리그 원점: 스틱 이동 · 스냅 회전 · 순간 이동 · 낙하) | 틱 입력으로 바로 계산하고, 서버가 아직 처리했다고 알리지 않은 입력을 보관합니다 | 같은 입력으로 같은 이동 함수를 돌려 결과를 정합니다 | 서버 상태로 되돌린 뒤 보관한 입력을 다시 실행합니다. 다시 실행하는 것은 그 캐릭터 하나입니다 |
| 추적 자세(머리 · 손 · 손가락) | 예측 대상이 아닙니다. 언제나 그리기 직전의 추적 값으로 그리고, 틱 입력에 실어 보냅니다 | 타당성을 검사한 뒤 채택합니다. 쥐기 · 타격 같은 판정은 서버가 채택한 자세로 합니다 | 서버는 한도 안으로 자른 값을 쓰고, 클라이언트의 화면은 고치지 않습니다 |
| 쥔 물체(D12) | 쥐기를 요청하는 순간 손에 붙여 그리고, 서버와 같은 따라가기 코드를 로컬에서 돌립니다 | 쥐기 판정과 물리를 정합니다 | 거절되면 손에서 풀고 서버 상태로 돌립니다 |
| 방금 놓거나 던진 물체, 손으로 민 물체 | 로컬 물리로 이어서 계산하고, 서버 상태가 오면 표시를 그쪽으로 줄여 맞춥니다(되감기 없음) | 물리를 정합니다 | 표시 오차를 짧은 시간에 줄입니다 |
| 그 밖의 물체와 다른 플레이어 | 서버 상태를 보간해 그립니다 | 정합니다 | 해당 없음 |

- **No Trust 대전에서 피할 수 없는 것은 셋입니다.**
  1. **자기 이동의 예측과 재실행.** 예측이 없으면 이동이 왕복 지연만큼 늦고, 클라이언트가 위치를 정하면 속도 · 벽 통과 조작을 막을 수 없습니다. 방식은 입력에
     순번을 붙여 보내고, 서버가 마지막으로 처리한 순번을 알려 주면, 클라이언트가 서버 상태에서 출발해 아직 처리되지 않은 입력을 다시 적용하는 것입니다 [LC2][U13].
     비용은 작습니다. 리그 이동이 쓰는 캐릭터 컨트롤러는 다른 몸을 밀지 않는 가상 캡슐이라(`PhysicsSystem.hpp` 150 ~ 153행) 물리 월드를 되감지 않고 이동 함수만
     다시 부르면 됩니다. 틱 60 Hz 에 왕복 150 ms 이면 보정 한 번에 약 9번입니다.
  2. **서버의 입력 검사와 입력 버퍼.** 서버는 틱 번호마다 입력을 하나만 쓰고, 클라이언트가 입력을 실제 시간보다 빨리 보내도 더 많이 움직이지 못하게 합니다.
     추적 자세의 타당성 검사도 여기에 듭니다(아래).
  3. **판정의 지연 보정.** D14 에서 따로 다룹니다.
- **여전히 하지 않는 것은 물리 월드 전체의 되감기입니다.** 근거는 초안과 같습니다. UE · Unity 에서도 범용 물리 예측은 실험 단계이거나 비용 경고가 붙어 있고(1-2),
  90 Hz 에서 지연 250 ms 를 숨기려면 프레임마다 물리를 약 25 스텝 돌려야 한다는 계산이 있으며 [GF4], Quest Pro 의 CPU 예산에 맞지 않습니다.
  치르는 값은 이렇습니다. 쥔 물체는 손 자세에서 바로 계산되므로 되감기 없이도 맞지만, **자기가 던지거나 밀친 물체가 로컬 화면에서 서버 결과와 잠깐 다르게 보일 수
  있습니다.** 던진 사람 화면에서는 맞은 것처럼 보였는데 서버 판정은 빗나감인 경우가 생깁니다. 줄이는 수단은 둘입니다. 서버와 클라이언트의 물리가 같은 입력에 같은
  결과를 내게 하는 것(Jolt 결정론 옵션, D5)과, 놓는 순간의 상태를 서버 값으로 빨리 확정하는 것입니다. UE 의 Predictive Interpolation 모드가 같은 종류의 타협입니다 [U17].
- **추적 자세의 타당성 검사(서버).** VR 샘플은 호스트 권위에서도 리그 자세를 절대값 입력으로 보내 그대로 쓰지만 [P4], 그 샘플은 검사를 하지 않습니다. 공개 대전에서는
  다음을 검사합니다.
  - 머리가 리그 원점에서 수평으로 벗어난 거리(놀이 영역 크기 한도)와 머리 높이 범위
  - 틱 사이의 머리 · 손 이동 속도 한도
  - 손과 머리 사이의 거리 한도(팔 길이에 여유를 더한 값)
  - 머리에서 손까지 사이에 벽이 있는가(벽 너머로 손을 뻗어 쥐거나 때리는 것을 막음)
  - 위반하면 한도 안으로 자른 값을 채택하고 횟수를 기록합니다. 추적이 잠깐 끊기는 것은 흔한 일이므로 한 번의 위반으로 제재하지 않으며, 제재 기준은 게임 정책입니다.
- **VR 에서 보정을 보여 주는 방법(설계 판단, 공식 자료를 찾지 못해 확신 낮음, 헤드셋 확인 필요):**
  - 순간 이동과 스냅 회전은 한 번에 일어나는 사건이라 예측이 잘 맞습니다. 서버는 포물선 · 거리 · 쿨다운을 다시 계산해 검사합니다.
  - 스틱 이동의 보정은 플레이어의 시점을 옮깁니다. 서버 결과와의 차이가 작은 허용 오차 안이면 보정을 보내지 않고, 넘으면 서버 위치로 **한 번에** 옮기면서 짧게
    화면을 어둡게 합니다(순간 이동과 같은 편안함 처리). 여러 프레임에 걸쳐 끌어당기지 않습니다.
  - 플레이어가 실제로 걸어서 머리가 벽을 지나는 경우는 아래 항목에서 따로 다룹니다.
- **실제로 걸어서 움직이기(2026-11-24 사용자 답 25: 스틱 이동이 전제, 위치 추적도 지원):**
  - **서버가 보는 몸은 캐릭터 캡슐입니다.** 캡슐은 스틱 이동과 "머리의 수평 움직임 따라가기" 두 가지로 움직이고, 둘 다 같은 "막히면 미끄러지는" 이동 함수를 지납니다.
    틱마다 지난 틱의 캡슐 자리에서 지금 머리 아래 자리까지를 훑어 옮기므로, 플레이어가 실제로 걸어도 캡슐은 벽을 지나지 못합니다. 자기 이동의 예측도 "스틱 입력 + 머리의
    수평 변위"를 한 틱의 이동 입력으로 묶어 같은 함수로 계산하고, 서버가 같은 입력으로 다시 실행합니다.
  - **지금 코드는 다릅니다.** 캡슐을 틱마다 머리 아래로 곧바로 옮긴 뒤 스틱 이동만 훑습니다(`XrComponents.cpp` 299 ~ 321행, 302행). 실제로 걸어 벽을 지나면 캡슐도 건너편에 놓입니다.
    충돌 이동 자체도 선택 항목이고 기본이 꺼짐입니다(`collide`, 388행). 서버 권위에서는 캡슐이 자기 자리를 기억하고 머리 쪽으로 훑어 가야 합니다(4절 P5).
  - **벽 통과:** 머리가 벽을 지나면 캡슐은 벽 앞에 남아 머리와 캡슐이 벌어집니다. 수평 거리가 한도(캡슐 반지름에 몸을 기울이는 여유를 더한 값)를 넘으면 서버는 그 플레이어를
    "몸 밖" 상태로 봅니다. 그동안 쥐기 · 공격 · 조작 요청을 거부하고, 맞는 형상은 캡슐 자리에 둡니다(머리를 벽 안에 숨겨 맞지 않으려는 것을 막음). 클라이언트는 화면을 가립니다.
    머리가 한도 안으로 돌아오면 풀립니다. 시점을 밀어내지 않습니다.
  - **오래 벗어나 있을 때:** 일정 시간 넘게 벗어나 있거나 거리가 크면 리그 원점을 옮겨 머리를 캡슐 위로 되돌립니다. 표시는 스틱 이동 보정과 같습니다(짧게 어둡게 하며 한 번에).
  - **플레이 영역 밖:** 서버는 클라이언트가 알려 주는 플레이 영역 크기를 믿지 않습니다. 머리가 리그 원점에서 수평으로 벗어난 거리에 서버 설정의 고정 상한을 두고, 틱 사이 머리
    이동에 사람이 낼 수 있는 속도 한도를 둡니다. 추적 좌표를 조작해 걷는 것보다 빨리 움직이는 것을 이 둘과 캡슐 충돌이 막습니다.
  - **높이:** 머리 높이가 바닥 아래이거나 사람 키 범위를 넘으면 잘라 씁니다. 앉기 · 숙이기는 정상 동작이므로 맞는 형상은 머리 높이를 따르되 하한을 둡니다.
  - **서버가 막지 못하는 것:** 머리만 벽에 넣어 건너편을 엿보는 것입니다. 화면은 클라이언트의 것이기 때문입니다. 조작하지 않은 클라이언트는 화면을 가리고, 조작한 클라이언트에는
    벽 너머 상대의 위치를 보내지 않는 정보 은닉("정하지 않고 남기는 것")이 수단이 됩니다.
  - 이 항목은 설계 판단입니다. 공식 자료를 찾지 못했습니다(확신 낮음). "화면을 가리고 그동안 쥐기 · 공격을 막는" 처리와 "짧게 어둡게 하며 한 번에 옮기는" 보정 표시는
    사용자가 받아들였고(사용자 답 34), 한도 값은 헤드셋에서 실험해 정합니다.
- **협동 방도 같은 검사를 합니다(사용자 답 23).** 한도 값은 방 종류와 무관하게 하나로 둡니다.
- **손 추적 대전은 다음 목표입니다(사용자 답 24).** 처음에는 대전의 쥐기 · 공격 입력을 컨트롤러로만 받습니다. 손 추적은 추적이 끊기는 일이 잦아 자세 검사 한도를 따로 잡아야 하므로,
  손 추적 플레이어의 대전 참여는 컨트롤러 대전이 선 뒤에 엽니다. 손가락을 아바타에 보여 주는 것(D12)은 처음부터 넣습니다.
- **비용:** 리그 이동을 "입력 + 이전 상태 → 새 상태" 함수로 떼기(`RigLocomotionComponent::tick`, `XrComponents.cpp` 221행부터, 4절 P5), 입력 보관과 재실행 · 서버 검사(네트워크 모듈),
  보정 표시(클라이언트). 초안의 "다"보다 큽니다(중간 ~ 큼).
- **정해야 하는 때:** 방향은 정해졌습니다. 이동 함수의 모양(P5)은 게임플레이 코드를 더 쌓기 전, 나머지는 네트워크 구현 때입니다.

### D8 전송 계층 라이브러리

| 선택지 | 내용 |
|---|---|
| **가(권장, 조건부)** | 엔진의 전송 인터페이스 뒤에 GameNetworkingSockets 공개 판 |
| 나 | 같은 인터페이스 뒤에 yojimbo + 연결 토큰을 내주는 작은 서비스 |
| 다 | ENet + 직접 만든 암호화 |
| 라 | 기성 넷코드 서비스(Photon Fusion Core 의 서버 권위 모드 등) |

- **달라진 전제:** 운영 형태가 전용 서버(D9)이므로 NAT 통과가 필요 없습니다. 초안이 "가"를 고른 큰 이유(리슨 서버를 위한 ICE)는 사라졌고, 두 후보의 차이는
  **인증 방식**과 **의존성 무게**로 좁혀졌습니다.
- **권장안:** 엔진 것인 전송 인터페이스(연결 · 신뢰 채널 · 비신뢰 채널 · 통계)를 두고 첫 구현은 프로세스 안 루프백으로 합니다(초안과 같음). 실제 전송은 6절 V2 실험으로
  정합니다. 실험 내용은 두 후보의 Android(NDK) · Linux 빌드와 인증 길의 확인입니다. 잠정 순위는 "가" 먼저입니다.
- **근거:**
  - yojimbo(netcode)는 설계 범위(전용 서버, 100명 이하)가 0절의 전제와 꼭 맞고 의존성이 가볍습니다. 대신 **연결 토큰이 반드시 있어야 붙습니다.** 토큰은 웹 백엔드가 만들어
    HTTPS 로 클라이언트에 주고, 백엔드와 전용 서버가 비밀 키를 함께 갖습니다. 토큰 없이 붙는 방식은 표준에 없습니다 [T10]. 인증되지 않은 패킷이 서버 자원을 쓰지
    못한다는 점은 공개 서버에 좋지만, 백엔드를 EOS 만으로 두면(D10) 토큰을 만들 곳이 없어 작은 서비스를 직접 운영해야 합니다.
  - GNS 는 암호화가 들어 있고 Linux 서버에 널리 쓰입니다. 접속한 뒤 클라이언트가 EOS 의 ID 토큰을 보내고 서버가 검증하는 "앱 수준 인증"으로 가면 직접 만든 백엔드가
    필요 없습니다. 다만 Steam 밖에서 인증서 없이 전송 연결을 여는 설정이 어떻게 되는지는 이번에 확인하지 못했습니다(확인 못 함). 의존성(protobuf · 암호 라이브러리)의
    NDK 빌드가 부담이고, 관리자는 Android 빌드를 직접 시험할 수 없었다고 밝혔습니다 [T9].
  - "가"가 실험을 통과하지 못하면 "나"로 갑니다. 그때의 토큰 서비스는 D9 의 서버 배정과 한 서비스로 묶을 수 있습니다.
  - Steam 의 전송과 중계망은 Quest 단독 앱에서 쓸 수 없습니다. 크로스플레이를 하지 않더라도 두 스토어에 같은 전송을 쓰면 코드 길이 하나로 유지됩니다.
- **비용:** 새 모듈 `net`(전송 인터페이스 + 루프백)은 작습니다. 외부 라이브러리는 CMake · Android · Linux 빌드와 라이선스 고지 작업이 따릅니다(중간).
- **정해야 하는 때:** 네트워크 구현 때(V2 실험 뒤).

### D9 전용 서버 · 리슨 서버

| 선택지 | 내용 |
|---|---|
| 가 | 전용 서버만 두고 리슨 서버 코드는 만들지 않습니다 |
| **나(권장)** | 운영은 Linux 전용 서버(사용자 결정). 리슨 서버는 **개발 · 시험용으로만** 남깁니다 |
| 다 | 클라우드 방이 권위를 중재하는 분산 권위. No Trust 에서 제외합니다 |

- **권장안:** 나.
- **리슨 서버를 남기는 까닭:** 리슨 서버는 Standalone 에 "접속을 받는다"만 더한 것이라(D1) 유지 비용이 작고, 에디터에서 Play 한 채 두 번째 클라이언트를 붙여 보는 시험에
  필요합니다. 공개 매치에는 내놓지 않습니다. 호스트가 권위를 가지므로 No Trust 에 어긋나기 때문입니다. 리슨 서버에서만 되는 코드가 생기는 것을 막으려고 자동 시험은
  전용 서버 실행 파일과 클라이언트 프로세스로 돌립니다(6절 N2).
- **방과 프로세스:** 프로세스 하나가 방 하나를 맡습니다(5절의 Jolt 전역 상태 제약과도 맞음). 인원은 서버가 8명에서 끊습니다(아홉 번째 접속은 거절). 사용자 답
  "무슨 일이 있어도 8명 이하로 작동"은 **8명이 찬 방에서 틱 시간과 대역폭이 반드시 예산 안에 들어야 한다**는 수락 조건으로 받아들였습니다. 가짜 클라이언트 8명을 붙인
  부하 시험이 그 확인입니다(6절 N5). 8명이면 대역폭 때문에 관심 영역을 둘 필요는 없습니다(D12 의 예산).
- **방 주인(사용자 답 9 · 18 · 19):** 전용 서버에는 "호스트의 기기"가 없으므로 방 주인을 **방을 연 플레이어의 신원**(D10 의 제품 사용자 ID)으로 정의하고 서버가 기억합니다.
  방은 방 목록에서 골라 들어가는 방식뿐이라(자동 매칭 없음) 모든 방에 주인이 있습니다.
- **주인이 나갔을 때: 일시 정지 → 기다림 → 폭파(사용자 답 18).**
  1. 주인의 연결이 끊기면(앱 종료 · 연결 시간 초과) 서버는 방을 일시 정지하고 모두에게 "주인을 기다리는 중"과 남은 시간을 알립니다.
  2. **서버 쪽 일시 정지는 시뮬레이션 틱을 멈추는 것입니다.** 틱 번호가 늘지 않으므로 물리 · 타이머 · 날아가던 물체 · AI 가 그대로 멈췄다가 이어집니다. 입력만 막고 틱을 계속
     돌리면 주인이 없는 동안 월드가 진행해 버리므로 택하지 않습니다. 서버 프로세스의 네트워크 처리(연결 유지 · 알림 · 재접속 받기)는 계속 돕니다.
  3. 정지 중에도 각자의 화면은 멈추지 않습니다. 자기 머리와 손은 추적 값으로 계속 그리고(화면을 얼리면 멀미가 남), 다른 사람의 머리 · 손도 표시용으로 계속 복제합니다.
     이동과 쥐기 · 공격 입력은 받지 않습니다. 쥐고 있던 물체는 정지한 자리에 남고, 재개할 때 손이 한도보다 멀어져 있으면 놓은 것으로 처리합니다(D12 의 한도 검사 그대로).
  4. 주인이 정해 둔 시간 안에 다시 들어오면 짧은 카운트다운 뒤에 틱을 다시 돌립니다. 들어오는 길은 아래의 "새로 입장"입니다.
  5. 시간 안에 오지 않으면 방을 끝냅니다. 모두에게 종료 이유를 알리고, 서버에 둔 데이터를 정리하고, 세션 등록을 지운 뒤 프로세스를 끝냅니다. 빈 서버를 다시 띄우는 것은
     프로세스 관리자의 몫입니다. 방을 프로세스째 버리므로 방 사이에 상태가 새지 않습니다.
  - **기다리는 시간은 기본 1분입니다(사용자 답 30).** 서버 설정 파일(`engine.ini` 와 같은 `이름=값` 줄 형식의 서버용 ini, 5절 S6)에서 바꿉니다. 대전 방에서 주인이 일부러 끊었다 붙으며
    정지를 악용하는 것을 막는 한도도 같은 파일의 항목입니다: 한 방에서 주인 때문에 멈출 수 있는 횟수와 멈춘 시간의 합. 한도를 넘은 뒤에 주인이 끊기면 기다리지 않고 방을 끝냅니다.
    기본값은 3회 · 합계 3분을 제안합니다. 주인이 스스로 "방 닫기"를 고르면 기다리지 않고 끝내고, 방이 "진행 중"이 되는 때는 주인이 시작을 누른 때로 제안합니다(7-2 질문 40).
- **끊긴 사람은 "다시 붙기"가 아니라 "새로 입장"입니다(사용자 답 31).** 이전 상태를 되살리는 재접속 길을 따로 만들지 않습니다.
  - 서버는 방이 시작될 때의 **명단**(자리마다 제품 사용자 ID)을 기억합니다. 진행 중인 방은 명단에 없는 계정의 접속을 거절하고(사용자 답 9-2: 새 사람은 못 들어옴), 명단에 있는 계정이
    다시 오면 받습니다. 이 해석이 맞는지는 7-2 질문 37 로 남겼습니다.
  - 연결이 끊기면 그 사람의 플레이어 액터를 지웁니다(쥐고 있던 물체는 놓은 것으로 처리). 다시 들어오면 **새 플레이어 액터로 시작 지점에서 시작**하고, 이전 위치 · 쥐고 있던 것 같은
    캐릭터 상태는 되살리지 않습니다. 엔진은 "자리"와 "플레이어 액터"를 나눠 둡니다. 팀이나 점수처럼 자리에 남길 기록이 있는지는 게임이 정합니다(질문 38).
  - 새로 들어온 클라이언트는 방의 지금 월드 상태를 받아야 하므로 **전체 상태 전송(D4)은 필요합니다.** 초안의 "늦은 접속"과 같은 기능이고, 새 사람을 막는 것은 기술이 아니라 명단 검사라는
    정책입니다. 나중에 난입을 허용하게 되더라도 검사만 바꾸면 됩니다.
  - **신원 확인:** 들어오는 클라이언트의 ID 토큰을 처음 접속 때와 똑같이 검증하고, 그 계정이 명단에 있는지 봅니다. IP 주소나 기기가 같을 것을 요구하지 않습니다(통신망이 바뀌어 끊긴
    경우가 흔함). 같은 계정의 옛 연결이 남아 있으면 끊습니다. 클라이언트가 들고 온 "원래 참가자" · "방 주인" 같은 값은 믿지 않습니다.
  - **방 주인도 같은 길로 들어옵니다(판단).** 주인의 재접속을 따로 두지 않고 "새로 입장 + 명단의 주인 자리와 대조"로 맞춥니다. 주인에게만 있는 것은 끊겼을 때의 일시 정지 · 기다림 · 폭파와,
    돌아왔을 때의 재개뿐입니다. 길이 하나라 구현과 시험이 줄어듭니다. 치르는 값은 **주인의 캐릭터도 이전 상태 없이 새로 시작한다**는 점입니다. 방이 멈춰 있었으므로 주인만 상태를 되살리는
    것도 가능하지만 그러면 재접속 길이 둘이 됩니다(질문 39).
  - 주인이 아닌 참가자가 끊겼을 때는 방을 멈추지 않습니다.
- **헤드셋을 벗거나 시스템 메뉴를 열 때(사용자 답 10 · 17):** 기본값은 실행 모드가 정합니다(D1). 싱글은 OS 가 요청하면 멈추고, 멀티는 멈추지 않습니다.
  - 멀티 세션에서 월드는 서버의 것이므로 한 사람의 초점과 상관없이 계속 돕니다. 초점을 잃은 플레이어는 입력이 없는 "자리 비움" 상태로 복제됩니다.
  - 멀티에서 게임 설정으로 "멈춤"을 고르는 것은 **방 규칙**입니다. "주인이 자리를 비우면 방 전체를 멈춤"을 서버가 위의 일시 정지와 같은 방식으로 집행합니다.
    대전 방에서는 악용되므로 위의 정지 한도를 함께 씁니다.
  - **싱글의 "멈추지 않음" 설정은 Quest 판에도 열어 둡니다(사용자 답 36). 기본값은 "멈춤"입니다.** 스토어 심사 위험: Meta 의 싱글 플레이 요건(필수)은 OS 가 요청하면 멈출 것을
    요구하므로 [M10], 플레이어가 고를 수 있는 설정이라도 심사에서 지적될 수 있습니다. 지적되면 Quest 판에서만 이 설정을 감추면 됩니다.
  - 초점을 잃은 동안 Quest 가 앱에 CPU 를 주어 연결이 유지되는지는 확인하지 못했습니다. 끊기면 위의 "새로 입장" 길을 탑니다.
- **처음 규모: 동시에 방 2개(사용자 답 21).** 자동 확장 없이 고정된 구성으로 시작합니다. 서버는 아시아(일본) 지역에 둡니다(사용자 답 32).
  - Linux 가상 기계 한 대에 `HarukaServer` 프로세스 2개를 서로 다른 포트로 띄워 둡니다. 프로세스 관리자(systemd 또는 컨테이너의 다시 시작 정책)가 끝난 프로세스를 다시 띄웁니다.
  - 빈 프로세스는 방 목록에 "빈 서버"로 등록되어 있다가, 방을 여는 사람이 들어오면 그 사람이 주인이 되고 그 스토어의 방으로 바뀝니다(D10). 그래서 프로세스 2개로 두 스토어를
    함께 받습니다. 한 스토어가 둘을 다 쓸 수도 있습니다.
  - 둘 다 쓰는 중이면 방 열기를 거절하고 "빈 서버가 없음"을 알립니다. 대기 줄은 두지 않습니다.
  - 기계의 크기(코어 수 · 메모리)는 8명 부하 시험(N5)에서 잰 프로세스 하나의 틱 시간으로 정합니다. 방 하나에 코어 하나를 온전히 주는 것에서 시작합니다(추정).
  - 방 수를 늘릴 때는 프로세스 수를 늘리고, 그다음이 기계 추가입니다. 자동 확장(Agones · Edgegap · GameLift)은 그 뒤의 일입니다.
- **서버 비용:** 틱 60 Hz 면 틱 하나의 예산이 16.7 ms 이고, 한 기계에 방을 몇 개 올릴 수 있는지가 운영비를 정합니다. VALORANT 는 서버 프레임을 2.34 ms 로 묶어 코어 하나에
  세 게임을 올렸다고 밝혔습니다 [R3]. Haruka 서버의 틱 시간은 재야 압니다.
- **비용:** 5절(전용 서버 실행 파일 · Linux)이 필수 작업이 되었습니다. 일시 정지와 새로 입장은 서버의 방 상태 기계 · 명단 · 전체 상태 전송이 듭니다(중간).
- **정해야 하는 때:** 운영 형태 · 처음 규모 · 지역 · 기다리는 시간은 정해졌습니다. 7-2 의 질문 37 ~ 40 은 6절 N6 전에 정합니다.

- **비공개 방(비밀번호 또는 초대한 사람만)은 나중 항목입니다(사용자 답 35).** 세션 속성 하나와 서버의 입장 검사를 더하는 일이라 구조를 바꾸지 않습니다.
- **이른 확인 항목(6절 V1):** 두 스토어에 내므로 **EOS 가 Quest 단독 앱에서 동작하는지**가 이 권장의 조건입니다. 음성도 같은 실험에서 확인합니다(D13). Epic 이 Quest 지원을 직접 적은 문장은 찾지 못했고,
  근거는 Android SDK · Meta 신원 공급자 · Meta 가 대안으로 Epic 을 거론했다는 점뿐이며, 로그인 실패를 겪었다는 포럼 글도 있습니다(1-5). 네트워크 구현을 시작하기 전에
  Quest 실기에서 "Meta 계정으로 로그인 → 세션 찾기 → 서버가 ID 토큰 검증"까지 해 봅니다. 막히면 "나"로 갑니다.
- **저장(사용자 답 8: 저장 데이터는 플레이어 기기, 서버에는 넘길 필요가 있는 것만):**
  - 개인 진행은 지금의 `SaveStore`([Save_And_Settings.md](Save_And_Settings.md))로 기기에 둡니다.
  - 서버로 넘기는 것은 방을 열 때 그 방의 월드가 될 저장본입니다. 저장 글 형식(값 줄 + CRC)을 그대로 보내고 서버가 크기와 형식을 검사합니다. 방이 끝나면 서버가 결과를
    주인에게 돌려주고 주인의 기기가 저장합니다.
  - No Trust 와 부딪히는 지점이 하나 있습니다. **기기에 둔 저장본은 플레이어가 고칠 수 있으므로 공개 대전의 판정에 쓸 수 없습니다.** 협동 방도 No Trust 이지만(사용자 답 23),
    방 주인이 올린 저장본은 그 방의 출발 상태일 뿐이라 주인 자신의 방에만 영향을 줍니다. 서버는 형식과 크기를 검사하고, 그 뒤의 진행은 서버가 정합니다.
  - **지속되는 진행을 대전에 반영하는 일은 나중입니다(사용자 답 22).** 지금은 대전이 매번 같은 조건에서 시작한다고 봅니다. 반영하게 되면 서버 쪽에 믿을 수 있는 기록이 필요하고,
    그때 기록을 둘 곳을 정합니다("정하지 않고 남기는 것").
- **두 스토어, 지금은 크로스플레이 없음(사용자 답 12 · 3 · 28 · 29):**
  - Meta Horizon Store(Quest 단독 판만 냄): 소유 확인, 사용자 신고 수단(필수), 혼합 연령이면 나이 범주 API(필수), 데이터 사용 승인, 초대 · Group Presence(선택) [M4][M6][M7].
  - Steam: PC 판에서 Steamworks 로 신원 · 초대를 붙입니다. 전송은 쓰지 않습니다(D8).
  - **스토어별로 방 목록을 나눕니다.** 세션의 스토어 속성으로 목록을 거르고, 서버는 접속한 클라이언트의 ID 토큰에 적힌 신원 공급자(Meta · Steam)가 그 방의 스토어와 같은지
    검사합니다. 클라이언트가 속성만 바꿔 다른 스토어의 방에 들어오는 것을 막기 위해서입니다. 토큰에서 플랫폼 정보를 읽을 수 있다는 것은 포럼 글 기준입니다(확신 낮음) [B11].
  - **나누는 기준은 "어느 스토어의 판을 실행했는가"입니다.** Meta Horizon Store 에는 Quest 단독 판만 내므로(사용자 답 29) 방 목록은 "Quest 단독"과 "Steam(PC)" 둘입니다.
    Quest 를 PC 에 연결해 Steam 판을 하는 사람은 Steam 쪽 방에 들어갑니다.
- **나눠서 출시하되, 나중에 설정만으로 크로스플레이를 켤 수 있는 구조를 유지합니다(사용자 답 28).**
  - **전용 서버 구조에서는 Quest 와 PC 가 서로 직접 맞출 것이 없습니다.** 클라이언트는 저마다 같은 서버와만 말하고, Quest 클라이언트와 Linux 서버를 맞추는 일(6절 V3)은 크로스플레이와
    무관하게 이미 해야 합니다. 그래서 켜는 일의 어려움은 넷코드가 아니라 아래 목록의 운영 쪽에 있습니다.
  - **지금부터 지킬 것(이것이 구조를 유지하는 비용입니다):**
    1. 서버 실행 파일은 하나입니다. 스토어별 서버 판을 만들지 않습니다.
    2. 프로토콜은 하나이고 판 번호를 세션 속성에 넣습니다. 같은 판끼리만 방 목록에 보입니다.
    3. **시뮬레이션에 쓰는 콘텐츠는 두 판이 같아야 합니다.** 씬 · 프리팹 · 충돌 메시 · 물리 설정이 해당합니다. 텍스처 압축이나 LOD 처럼 판마다 달라도 되는 표시용 콘텐츠와 나눠서,
       접속 때 비교하는 해시(D3)는 시뮬레이션 콘텐츠만으로 만듭니다. Quest 판의 성능을 맞추려고 충돌 형상이나 물체 수를 판마다 다르게 하면 이 조건이 깨집니다.
    4. 방을 나누는 것은 설정입니다. 서버 설정 파일의 항목 하나("스토어별" 또는 "섞음")가 방 목록의 풀 표시와 신원 공급자 검사를 함께 정합니다.
    5. 스토어에 기대는 전송(D8)과 음성(D13)을 쓰지 않습니다. 둘 다 이미 스토어 중립입니다.
  - **켤 때 따로 필요한 것:**

    | 항목 | 내용 |
    |---|---|
    | 방 목록의 풀 표시 | 세션 속성에 "Quest 단독 · Steam · 섞음"을 두고, 섞인 방임을 목록에서 알 수 있게 합니다. 섞인 방에 들어갈지를 플레이어가 고르는 설정도 필요합니다 |
    | 안티 치트의 비대칭 | Easy Anti-Cheat 는 PC 에만 있습니다. 섞인 방에서는 PC 접속자에게만 확인을 요구하고 Quest 접속자는 면제해야 하는데, 이렇게 접속자별로 다르게 할 수 있는지는 확인하지 못했습니다(확인 못 함). **섞인 방의 방어선은 Quest 쪽과 같이 서버 권위 자체**이고, 그 사실을 PC 플레이어가 알 수 있게 합니다 |
    | 판이 어긋나는 기간 | 두 스토어의 심사 일정이 달라 한쪽만 새 판인 기간이 생깁니다. 판 번호가 다르면 서로의 방이 보이지 않으므로(위 2), 섞인 방을 유지하려면 두 스토어의 출시일을 맞추거나 서버가 옛 판의 방도 함께 받아야 합니다 |
    | 초대와 친구 | 친구 목록과 초대가 스토어마다 따로입니다. 섞인 방으로 부르려면 방 코드 같은 스토어 중립 수단이 필요합니다 |
    | 차단 | 스토어가 다른 사람 사이에는 플랫폼의 차단 목록이 자동으로 적용되지 않을 수 있어(D13) 게임이 직접 맡습니다 |
    | 형평 | PC 는 프레임 빈도와 성능이 높습니다. 시뮬레이션 틱은 같으므로 판정은 같지만, 보이는 품질과 추적 방식의 차이가 대전에서 문제가 되는지 시험합니다 |
    | 스토어 정책 | 각 스토어가 다른 스토어 사용자와의 대전에 붙이는 조건을 확인합니다(확인 못 함) |
- **Rust 직접 제작:** 권장에서 뺐습니다. 직접 만들 일이 생기는 경우는 서버 자동 배정, 믿을 수 있는 서버 쪽 진행 기록, yojimbo 의 토큰 서비스(D8) 정도이고, 그때 언어를
  고르면 됩니다. 게임 서버가 C++ 라는 판단은 그대로입니다(1-5).
- **업체에 묶이지 않기:** 2026년에 호스팅 업체 두 곳이 사라졌으므로 서버는 평범한 Linux 컨테이너로 만들고 업체 SDK 호출은 얇은 층 뒤에 둡니다.
- **비용:** 인터페이스는 작습니다. EOS 구현체와 플랫폼 SDK 연동은 중간입니다.
- **정해야 하는 때:** 방향은 정해졌습니다. V1 은 네트워크 구현을 시작하기 전에 합니다.

  큐입니다(규칙 3). 에셋 워커(2026-11-20)와 같은 모양입니다. 암호화와 소켓 호출이 메인 스레드에서 빠지므로 VR 프레임 마감에 유리합니다. "가"도 규칙 안에
  있고 더 단순하므로, 전송 라이브러리가 호출한 스레드에서만 도는 종류면 "가"로 시작해도 됩니다. "다"는 복제 대상이 수천 개가 될 때의 일입니다.
- **문서에 미치는 영향:** [Layer_Architecture.md](Layer_Architecture.md) 115행이 든 "단일 스레드 전제와 충돌"은 이 구조에서는 성립하지 않습니다. 판정을 바꿀 때 `Threading.md` 의 스레드 표에

### D12 VR 자세 복제와 쥐기 판정

초안은 "쥔 사람이 권위를 갖고 서버가 중재"를 권장했습니다. 공개 매치 No Trust(0절)에서는 클라이언트가 물체의 상태를 정할 수 없으므로 **서버가 모든 판정을 하는
방식**으로 다시 씁니다.

**자세(머리 · 손 · 손가락)**

- 추적 자세는 **입력**입니다. 틱 입력에 리그 기준 절대 자세로 실어 서버에 보내고, 서버는 D7 의 검사를 거쳐 채택한 뒤 다른 사람에게 복제합니다.
- 로컬에서는 언제나 그리기 직전의 추적 값으로 그립니다(지금 `TrackedPoseComponent::tick` 이 하는 일). 서버가 값을 잘라 채택했더라도 자기 화면의 머리 · 손은 고치지 않습니다.
- 원격 아바타는 지터 버퍼(100 ms 안팎에서 시작)로 보간합니다. `TrackedPoseComponent` 는 "로컬이면 추적 값, 원격이면 복제 값 보간"의 두 길을 갖게 됩니다.
- 아바타는 상반신입니다(사용자 답 13). 가슴과 팔꿈치는 받는 쪽이 머리 · 손 자세에서 계산하므로 따로 보내지 않습니다.
- 손 추적을 지원합니다(사용자 답 13). 손가락은 두 가지 모양으로 보냅니다.
  - 컨트롤러를 쥔 플레이어: 손가락 굽힘 값 다섯 개(트리거 · 그립 · 터치에서 나온 값). 받는 쪽이 같은 `HandPoseComponent` 로 손 모양을 다시 만듭니다([Hand_Grasp_Design.md](Hand_Grasp_Design.md) B 단계).
  - 손 추적 플레이어: 관절 회전 24개를 관절별 자유도와 가동 범위에 맞춰 양자화합니다. 굽히기만 하는 마디는 한 축, 벌릴 수 있는 첫 마디는 두 축으로 줄이는 방식이고,
    한 손 18 ~ 19 바이트로 줄인 공개 사례가 있습니다 [P7].
  - 손가락은 판정에 쓰지 않습니다. 서버는 값의 범위만 보고, 쥐려는 뜻(집기 · 주먹 쥐기의 세기)은 클라이언트가 "쥐기" 입력으로 바꿔 따로 보냅니다.

**8명 예산(추정: 아래 양자화 가정으로 계산한 값이고 구현해 잰 값이 아님)**

| 항목 | 가정 | 크기 |
|---|---|---|
| 머리 · 손 자세 하나 | 위치는 리그 기준 1 mm 눈금 16비트 × 3, 회전은 가장 큰 성분을 뺀 세 성분 32비트 | 10 바이트 |
| 리그 원점 | 월드 위치와 요 각 | 10 바이트 |
| 손가락 | 손 추적은 한 손 19 바이트, 컨트롤러는 두 손 합쳐 약 7 바이트 | 38 또는 7 바이트 |
| 상태(추적 유효 · 쥔 물체 번호 등) | | 약 5 바이트 |
| **아바타 하나** | 머리 + 두 손 + 리그 + 손가락 + 상태 | 손 추적 약 83, 컨트롤러 약 52 바이트 |

| 방향 | 계산 | 결과 |
|---|---|---|
| 서버 → 클라이언트 한 명 | 다른 7명 × 83 바이트 × 초당 30회 + 패킷 머리 | 약 19 kB/s(약 150 kbit/s). 모두 컨트롤러면 약 12 kB/s |
| 서버가 보내는 합계 | 위 × 8명 | 약 150 kB/s(약 1.2 Mbit/s). 아바타만 센 값 |
| 클라이언트 → 서버 | 자기 자세 · 손 속도 · 이동 입력 · 틱 번호에 직전 입력의 중복분을 더해 약 136 바이트 × 초당 60회 + 패킷 머리 | 약 11 kB/s(약 90 kbit/s) |

- 손가락을 자세의 절반 빈도로 보내고 변화가 없으면 생략하면 더 줄어듭니다. 참고로 Fiedler 의 VR 샘플은 플레이어당 256 kbit/s 이하를 목표로 삼았습니다 [GF4].
- 8명에서는 아바타 대역폭이 걸림돌이 아닙니다. 물체 상태의 예산은 게임이 물체를 몇 개 움직이는지에 달려 있어 N5 의 부하 시험에서 잽니다.

**쥐기 · 놓기 · 빼앗기 · 함께 들기**

| 선택지 | 내용 |
|---|---|
| 가 | 쥐기를 예측하지 않습니다. 서버가 승인한 뒤에 손에 붙습니다 |
| 나 | 쥔 사람에게 권위를 넘깁니다. **초안의 권장안이었으나 철회합니다** |
| **다(권장)** | 서버가 판정하고, 쥐는 사람의 클라이언트는 결과를 앞서 보여 준 뒤 서버 결과로 바로잡습니다 |

| 행동 | 클라이언트 | 서버 |
|---|---|---|
| 쥐기 | 틱 입력에 "쥐기 눌림"과 고른 대상을 싣고, 바로 손에 붙여 그립니다(연출인 햅틱도 바로) | 그 틱에 채택한 손 자세로 잡을 대상 고르기를 다시 실행합니다(거리 · 반경 · 차폐 · 이미 쥔 사람). 승인하면 쥔 사람을 기록해 복제하고, 거절하면 알립니다 |
| 쥔 동안 | 서버와 같은 따라가기 코드를 자기 추적 손으로 돌립니다. 다른 사람의 쥔 물체는 "어느 손 + 손 기준 상대 자세"로 받아 그 사람의 보간된 손에 붙여 그립니다 | 채택한 손 자세로 물체를 움직입니다. 물체는 물리 몸으로 남아 벽에 막힙니다. 손과 물체가 한도보다 멀어지면 서버가 놓게 합니다 |
| 놓기 · 던지기 | 놓는 순간부터 로컬 물리로 날아가는 모습을 그리고 서버 상태로 줄여 맞춥니다(D7) | **던지는 속도는 서버가 계산합니다.** 입력에 실린 손 속도를 자세 변화와 맞는지 검사한 뒤 지금과 같은 식(손 속도 이력의 평균)으로 구합니다 |
| 빼앗기 | 쥐기와 같은 요청입니다. 빼앗긴 쪽은 서버 통지를 받고 손에서 풉니다(미리 알 수 없는 사건이라 보정이 보임) | 물체의 설정(아래 표)으로 판정합니다 |
| 함께 들기 | 물체를 로컬 물리로 앞서 계산합니다. 자기 손의 연결은 추적 값으로, 상대 손의 연결은 복제된 자세로 넣고 서버 상태로 줄여 맞춥니다. 물체가 자기 손만 따르지 않으므로 손 모델을 물체의 쥔 자리에 붙여 그립니다 | 물체는 움직이는 몸으로 두고, 쥔 손마다 조인트로 잇습니다([Physics_Joints_And_Events.md](Physics_Joints_And_Events.md) D5). 서버 물리가 결과를 정합니다 |

- **빼앗기와 함께 들기는 기본 기능입니다(2026-11-24 사용자 답 26).** 특정 물체를 위한 기능이 아니라 쥘 수 있는 모든 물체가 갖고, 물체마다 켜고 끕니다.
  - `GrabbableComponent` 에 설정 칸 둘(함께 들기 허용 · 빼앗기 허용)을 둡니다. 지금 있는 `throwable` 과 같은 자리이고 디테일 패널에서 바꿉니다. 기본값은 둘 다 켬이며,
    씬 파일에는 기본값과 다를 때만 써서 옛 씬이 그대로 읽히게 합니다.
  - 이미 쥔 물체를 다른 사람이 쥐려 할 때 서버가 하는 판정은 두 칸의 조합으로 정해집니다.

    | 함께 들기 | 빼앗기 | 두 번째 사람이 쥐면 |
    |---|---|---|
    | 켬 | 켬 | 같이 듭니다. 서로 당겨 한쪽 손의 연결이 한도를 넘으면 그 손이 놓칩니다(힘겨루기가 곧 빼앗기) |
    | 켬 | 끔 | 같이 듭니다. 한도를 넘으면 나중에 쥔 쪽이 놓칩니다 |
    | 끔 | 켬 | 나중에 쥔 사람이 가져가고 먼저 쥔 사람은 놓칩니다 |
    | 끔 | 끔 | 거절합니다 |

  - 한 사람이 두 손으로 한 물체를 쥐는 것도 같은 구조(쥔 손 여러 개)로 처리됩니다.
  - 기본 기능이므로 쥐기를 "요청 → 판정 → 적용"으로 나눌 때(4절 P4) **처음부터 쥔 손이 여럿인 자료 구조로** 만듭니다. 나중에 하나에서 여럿으로 바꾸면 쥐기 위에 얹은 코드를
    다시 고쳐야 합니다. 연결의 한도 값과 힘겨루기의 느낌은 헤드셋에서 조정할 값입니다.
- **협동 방도 같은 판정을 합니다(사용자 답 23).** 손 추적 플레이어의 손가락은 처음부터 보여 주지만, 대전에서 손 추적으로 쥐고 공격하는 것은 컨트롤러 대전 다음의 목표입니다(사용자 답 24, D7).
- **근거:**
  - "가"는 쥐는 반응이 왕복 지연만큼 늦어 VR 에서 쓰기 어렵습니다. "나"는 클라이언트가 물체를 원하는 자리에 둘 수 있어 No Trust 에 어긋납니다.
  - 쥔 물체의 자리는 "손 자세 × 쥔 자리"로 정해지므로, 같은 손 자세를 넣으면 서버와 클라이언트가 같은 결과에 닿습니다. 그래서 되감기 없이 예측할 수 있습니다.
    Fusion 의 호스트 권위 VR 샘플도 쥐기를 입력으로 보내고 로컬에서 먼저 보여 줍니다 [P4].
  - 던지는 속도를 클라이언트가 정하면 물체를 원하는 속도로 날릴 수 있습니다. 지금은 놓는 쪽이 계산합니다(`XrComponents.cpp` 651 ~ 657행).
  - 함께 들기는 공식 샘플을 찾지 못했습니다(확인 못 함). 위 방식은 설계 판단이며 실험이 필요합니다. 쥐기 기능 가운데 가장 어렵습니다.
- **지금 코드와의 거리:**
  - `GrabInteractorComponent` 의 `grab` · `release`(`XrComponents.cpp` 477 · 593행)가 판정과 적용을 한 번에 합니다. "요청 → 판정 → 적용"으로 나눕니다(4절 P4). 싱글에서는 요청이 바로 승인됩니다.
  - 쥔 동안 물체를 옮기는 길이 둘입니다. 속도를 넣어 따라가게 하는 길(579 ~ 587행)과 자세를 바로 쓰는 길(589 ~ 590행)입니다. 자세를 바로 쓰면 물체가 벽을 지나므로,
    서버 권위에서는 **속도로 따라가는 길이 기본**이 되어야 합니다.
  - 쥔 사람을 가리키는 값이 하나뿐입니다(`holder_`). 함께 들기에는 여러 손을 담는 자료 구조가 필요하고, 포인터는 플레이어 정체성(D1)으로 바뀝니다.
  - 자동 맞춤 쥐기가 정하는 쥔 자리(`fitGrasp`, 512행)는 XR 모듈의 풀이를 씁니다. 풀이는 클라이언트가 하고 결과인 쥔 자리만 요청에 실어 서버가 한도(손에서의 거리)를
    검사하면, 서버가 XR 모듈을 끌어오지 않습니다(5절).
- **비용:** 쥐기 컴포넌트 둘의 재구성, 여러 손 쥐기, 서버 검사, 예측과 바로잡기. 큽니다.
- **정해야 하는 때:** "요청 → 판정 → 적용" 모양과 쥔 손이 여럿인 자료 구조(P4)는 게임플레이 코드를 더 쌓기 전. 구현은 6절 N4.

### D13 음성

**확정(2026-11-24 사용자 답 7): 게임 안 음성은 EOS 음성을 씁니다.** 초안의 "음성 없이 시작"과 직접 제작은 접습니다. 직접 만드는 길(Opus + 반향 제거 + 지터 버퍼)은 EOS 음성이
Quest 에서 되지 않을 때의 대안으로만 남깁니다.

**구조**

- **신뢰 서버 방식으로 붙입니다.** EOS 음성에는 로비에 붙여 쓰는 방식과, 신뢰하는 서버가 "누가 어느 방에 들어갈 수 있는가"를 정하는 방식이 있습니다 [EV1]. 로비 방식은 퇴장을 로비 주인인
  클라이언트가 하고 강제 음 소거가 없어(조사 원본 기준) No Trust 에 맞지 않습니다. 게임 서버가 방 입장 토큰을 받아 자기 넷코드로 **그 플레이어에게만** 전달하고, 클라이언트는 그 토큰으로 입장합니다.
- **Linux 서버는 음성 SDK 를 쓰지 않고 Web API 만 부릅니다.** 문서가 "Linux 는 지금 EOS 음성을 지원하지 않는다"고 적기 때문입니다 [EV1]. 토큰 발급 · 강제 퇴장(토큰도 폐기) · 강제 음 소거는 모두
  Web API 로 됩니다 [EV2]. 서버가 음성 데이터를 다루지 않으므로 필요한 것은 HTTPS 요청을 보내는 기능 하나입니다(5절 S6). 서버용 자격은 서버에만 둡니다.
- **음성 데이터는 게임 서버를 지나지 않습니다.** 인증된 사용자끼리 Epic 의 음성 서버를 거쳐 오가고, 저장되거나 녹음되지 않습니다 [EV1]. 게임 서버의 대역폭과 틱 시간에 영향이 없습니다.
  클라이언트는 밖으로 나가는 UDP 가 열려 있어야 합니다(조사 원본 기준).
- **방 구성:** 음성 방 하나의 상한은 64명이라(SDK 1.16 이상) [EV1] 8명 방에는 넉넉합니다. 협동 방은 게임 방 하나에 음성 방 하나, 대전 방은 팀마다 음성 방을 따로 둡니다.
- **가까이 가야 들리는 음성(3D 위치)은 둘째 단계입니다.** SDK 가 재생을 맡지 않게 하고 참가자별 소리 버퍼를 받아 엔진의 3D 음원(소리 버스 `voice`, [Save_And_Settings.md](Save_And_Settings.md) D7)에 넣는 길이 있습니다
  [EV3]. 버퍼는 SDK 의 스레드에서 오므로 뮤텍스로 지킨 큐로 넘깁니다([Threading.md](Threading.md) 규칙 3). 다만 이렇게 하면 SDK 가 스피커로 나가는 소리를 모르게 되어 반향 제거가 제대로 되는지
  불확실합니다(확신 낮음). Quest 는 스피커가 열려 있어 영향이 큽니다. 그래서 첫 단계는 SDK 가 재생하는 방 음성(위치 없음)으로 하고, 3D 위치는 실기 확인 뒤에 넣습니다.
- **No Trust 와 만나는 지점:** 음성은 Epic 서버가 방의 모두에게 전달하고, 거리에 따른 감쇠는 받는 클라이언트가 합니다. 조작한 클라이언트는 멀리 있는 사람의 소리도 들을 수 있습니다.
  상대에게 들리면 안 되는 말(대전의 작전)을 서버가 막는 수단은 **음성 방을 나누는 것**뿐입니다.
- **초점을 잃었을 때:** SDK 의 기본 동작은 앱이 뒤로 가면 음성 방을 나가는 것입니다(조사 원본 기준). D9 의 "자리 비움"과 맞고, 돌아오면 서버에 토큰을 다시 요청합니다.

### D14 판정의 지연 보정

대전이 들어오면서 새로 생긴 항목입니다. 쏘는 사람의 화면은 상대를 과거의 자리에 그립니다(왕복 지연 + 보간 지연만큼). 서버가 지금 자리로 판정하면 화면에서 맞힌 것이
빗나갑니다. 사용자 답 20("VR 게임 표준을 조사해서 적절한 것으로")에 따라 조사한 뒤 권장안을 정했습니다.

**조사 결과(2026-11-24)**

- **VR 대전 게임이 판정 방식을 직접 밝힌 1차 자료는 매우 적습니다.** Pavlov · Onward · Contractors · Population: One · Ghosts of Tabor · Gorilla Tag · Rec Room · Thrill of the Fight 2 등
  스무 개 남짓을 찾았지만 넷코드와 판정 주체를 개발사가 설명한 글을 찾지 못했습니다(확인 못 함). **"VR 게임의 표준"이라고 부를 만큼 공개된 것은 없고**, 아래 셋이 찾은 전부입니다.
  - Breachers(VR 전술 슈팅, Photon Fusion): 지연 보정을 "이런 슈팅 게임에 꼭 필요한 기능"이라고 하고, 캐릭터 · 손 · 머리의 움직임을 입력 권한으로 구동한다고 밝혔습니다 [LC10].

    부릅니다 [LC11]. 서버가 판정하는 구조가 아니므로 No Trust 에는 그대로 쓸 수 없습니다.

  걸쳐 있고, 경쟁 성격이 강할수록 짧습니다.
- 근접 중심 게임은 되감기의 불공정("막았는데 맞음")을 입력 지연으로 풉니다. **VR 에서는 손이 곧 아바타라 손 입력을 늦출 수 없으므로 이 방법을 쓸 수 없습니다.**

**권장안**

| **나(권장)** | 판정에 쓰는 **플레이어의 맞는 형상만** 과거 틱의 자세로 보관하고, 행동마다 다른 규칙으로 판정합니다(아래 표) |
| 다 | 물리 월드 전체를 과거로 되돌려 판정합니다 |

| 행동 | 판정 | 되돌리는 상한(시작값) | 근거 |
|---|---|---|---|
| 즉시 맞는 무기 · 빠른 탄 | **쏜 사람 기준으로 되돌려** 판정. 빠른 탄은 틱마다 지난 자리에서 새 자리까지의 구간을 되돌린 형상에 대어 봄 | **200 ms** | 일반 대전 게임의 표준 [LC3][LC5][LC6], VR 에서는 Breachers [LC10] |

- **이력:** 서버가 플레이어마다 맞는 형상(상반신 캡슐 · 머리 · 두 손 · 손에 든 무기)의 자세를 **16틱** 보관합니다(60 Hz 에서 약 267 ms, Unity 의 기본값과 같음). VR 에서는 맞는 형상이
  추적 자세에서 나오므로 몸의 위치만이 아니라 서버가 채택한 머리 · 손 자세 전체가 이력에 들어갑니다(VALORANT 가 애니메이션 자세까지 되돌리는 것과 같은 이유). 무적 · 방패 같은
  판정 상태도 같은 이력에 넣습니다. 물리 월드는 되돌리지 않고, 보관한 자세에 대해 광선 · 훑기 계산을 직접 한 뒤(`math/Geometry`) 벽 같은 정적 장애물은 지금 월드에 광선을 쏘아 확인합니다.
- **되돌리는 양:** 클라이언트가 입력에 실어 보낸 "내가 보던 틱과 틱 사이 비율"로 정합니다. 서버가 재는 지연 추정과 크게 어긋나면 서버의 추정을 씁니다(Source 가 200 ms 를 기준으로
  하는 검사와 같은 구조 [LC3]). 상한을 넘는 지연은 쏘는 쪽이 감수합니다.
- **상한을 200 ms 로 잡은 까닭:** 공개된 값 가운데 경쟁 성격이 강한 쪽의 값이고, 방이 8명 이하이며 서버를 가까운 지역에 두는 구성(D9)에서는 대부분의 플레이어가 이 안에 듭니다.
  되돌리는 양은 대략 "왕복 지연 + 원격 아바타의 보간 지연"이므로, **대전에서는 원격 아바타의 지터 버퍼(D12 의 시작값 100 ms)를 짧게 잡을수록** 같은 상한으로 더 큰 왕복 지연을 받아 줄 수
  있고 "엄폐한 뒤에 맞음"도 줄어듭니다. 세 상한은 서로 다른 서버 설정 값으로 두고, 지연을 흉내 낸 시험(예: 50 · 150 · 500 ms [LC7])으로 조정합니다.
- **무기끼리 부딪혀 밀리는 움직임은 서버 물리로 풀지 않습니다.** 서버는 "부딪혔다"는 사건(시각 · 접점 · 세기)만 정하고, 각 클라이언트가 자기 손의 반응(진동, 손과 무기 모델의 어긋남)을
  연출합니다. Broken Edge 도 칼끼리의 물리를 시뮬레이션하지 않았습니다 [LC11].
- **연출의 시점:** 총구 불꽃 · 휘두르는 소리처럼 자기 행동의 연출은 바로 내고, 명중 · 피해 · 처치의 연출은 서버 확인 뒤에 냅니다(VALORANT 와 같은 방식 [LC6]). 공격자 화면에서
  맞은 것처럼 보였다가 "막힘"이 될 수 있기 때문입니다.
- **던지기에서 놓는 순간:** 놓기 입력은 틱 번호에 묶여 서버가 그 틱에 실행하므로(D2 의 틱 입력), 제때 도착한 입력에는 따로 앞당겨 굴릴 것이 없습니다. 늦게 도착한 입력은 도착한 틱에
  실행하고, UT4 처럼 지연만큼 앞당겨 굴리는 처리는 필요해지면 설정으로 더합니다. 받는 쪽에 짧은 유리함을 주는 처리(Echo VR 의 사례는 검색 요약으로만 확인, 확신 낮음)는 처음에는
  두지 않습니다.
- **순간 이동과 되살아남:** 이력에 표시해 그 너머로는 되돌리지 않습니다(Source 도 크게 순간 이동한 플레이어는 되돌리지 않음 [LC3]).
- **치르는 값:** 맞는 쪽은 엄폐물 뒤로 숨은 직후에 맞을 수 있습니다 [LC1]. 근접에서는 서로 다른 지연을 가진 두 사람이 서로를 과거로 보므로, 어떤 규칙을 택해도 한쪽 화면과 어긋나는
  순간이 남습니다. 이 문제의 답을 밝힌 VR 자료는 찾지 못했으므로, 근접 판정의 기준(공격자 기준 · 서버 시각 기준 · 막기 우선)을 설정으로 바꿀 수 있게 만들어 헤드셋에서 비교합니다.
- **비용이 작은 까닭:** 8명 × 형상 5개 안팎 × 16틱은 자세 약 640개입니다. 메모리와 계산이 모두 작습니다. "다"는 D7 에서 피한 물리 월드 되감기를 서버에 들이는 일이라 택하지 않습니다.
- **비용:** 서버의 자세 이력과 판정 함수(네트워크 모듈 + 게임 쪽 무기 코드). 중간입니다.
- **정해야 하는 때:** 방식은 위 권장안으로 두고, 상한 값은 6절 N5 의 시험에서 조정합니다. 처음 대전은 컨트롤러 입력만 받습니다(D7).

### 정하지 않고 남기는 것

- **정보 은닉:** 8명이면 대역폭 때문에 관심 영역을 둘 필요는 없지만, 대전에서는 벽 너머 상대의 위치를 보내지 않는 것이 엿보기 방지 수단이 됩니다.
- **상태를 되살리는 재접속 · 난입 · 호스트 이전:** 끊긴 사람은 새로 입장으로 다루므로(D9) 이전 상태를 되살리는 재접속은 만들지 않습니다. 진행 중인 방에 새 사람이 들어오는 난입은
  명단 검사로 막아 두었고, 허용하게 되면 검사만 바꿉니다. 방 주인이 돌아오지 않으면 방이 끝나므로 호스트 이전은 필요 없습니다.
- **비공개 방:** 비밀번호나 초대한 사람만 들어오는 방입니다(사용자 답 35: 나중).
- **지속되는 진행의 서버 쪽 기록:** 해금한 장비나 등급을 대전에 반영하게 되면 필요합니다(사용자 답 22: 나중). 기기의 저장본은 믿을 수 없으므로 서버가 쓰는 기록이어야 합니다.
- **크로스플레이 켜기:** 지금은 나눠서 출시합니다(사용자 답 3 · 28). 켤 수 있는 구조를 유지하는 조건과 켤 때 필요한 것은 D10 에 적었습니다.
- **리플레이:** 서버가 입력과 상태를 기록해 두면 신고 처리와 부정행위 조사에 쓸 수 있습니다.
- **세션 중 씬 전환:** 지금 `requestScene` 은 게임 실행 파일의 로컬 전환이며, 서버가 이끄는 전환으로 바꿔야 합니다.
- **프로토콜 버전 호환, 서버 감시와 통계 기반 부정행위 탐지, 봇 · 관전자.**

## 3. 싱글만 만드는 동안에도 지켜야 할 규칙

비용이 작고, 지키지 않으면 나중에 게임플레이 코드를 훑어 고쳐야 하는 것만 모았습니다. R1 ~ R3 는 엔진 쪽 준비(D1 · D2)가 먼저 있어야 지킬 수 있습니다.

| R11 | **다시 실행될 수 있는 코드(이동)는 "입력 + 이전 상태 → 새 상태"만 계산합니다.** 소리 · 햅틱 · 액터 생성 · 이벤트 같은 부수 효과를 그 안에서 일으키지 않습니다(2026-11-24 추가) | 서버와 어긋나면 클라이언트가 같은 틱을 여러 번 다시 실행합니다(D7). 부수 효과가 안에 있으면 그때마다 다시 일어납니다 | 리그 이동 안의 순간 이동 햅틱과 디버그 선(`XrComponents.cpp` 369 · 374행) |
| R12 | **요청에는 "무엇을 하고 싶다"만 담고 결과를 담지 않습니다.** 판정에 쓰는 값(던지는 속도 · 맞은 대상 · 피해량)은 판정하는 쪽이 계산합니다(2026-11-24 추가) | 공개 매치에서 서버는 클라이언트가 보낸 값을 믿지 않습니다. 결과를 요청하는 쪽이 계산하는 코드는 서버 쪽으로 전부 옮겨 써야 합니다 | 던지는 속도를 놓는 쪽이 계산(`XrComponents.cpp` 651 ~ 657행) |

게임 디자인 쪽에서 미리 알아 둘 점도 하나 있습니다. 멀티 세션에서는 한 사람이 메뉴를 열어도 월드가 멈추지 않으므로, "일시정지하면 안전하다"에 기대는 규칙은 만들지 않는 편이 좋습니다.

## 4. 싱글 작업에 먼저 넣을 엔진 쪽 준비

3절의 규칙을 코드로 지킬 수 있게 하는 최소한입니다. 네트워크 코드는 한 줄도 들어가지 않습니다.

| 순서 | 내용 | 결정 | 크기 | 상태 |
|---|---|---|---|---|
| P1 | 권위 질의 API(`isServer` · `hasAuthority` · `netRole` · 플레이어 정체성과 로컬 플레이어 질의). 모두 상수를 돌려줌. 초점을 잃었을 때의 기본 동작을 실행 모드가 정하게 하고 게임 설정으로 바꿀 수 있게 함 | D1 · D9 | 작음 | 제안 |
| P2 | 고정 시뮬레이션 틱(기본 60 Hz) + 표시 단계 + 추출 단계의 표시 보간, 헤드셋 주사율 맞춤 제거 | D2 | 묶음 3 ~ 4개 + 헤드셋 확인 | **진행 중**(2026-11-24 사용자 결정) |
| P3 | 틱 입력: 축 · 동작 · 머리와 손 자세 · 손가락 · 쥐기 의도를 틱 번호와 함께 담은 값 묶음을 플레이어별로 두고, 컴포넌트 5곳이 그것을 읽게 바꿈 | D2 · D7 · R2 | 중간 | P2 뒤 |
| P4 | 쥐기를 "요청 → 판정 → 적용"으로 나누고 판정과 연출을 분리. 던지는 속도 계산을 판정 쪽으로 옮김. 쥔 손을 여러 개 담는 자료 구조와 `GrabbableComponent` 의 함께 들기 · 빼앗기 설정 칸(싱글에서는 한 사람의 양손 쥐기로 확인) | D12 · R3 · R12 | 중간 ~ 큼 | P3 뒤 |

## 5. 전용 서버 실행 파일 (Linux)

운영 형태가 Linux 전용 서버로 정해졌으므로(D9), 초안이 미뤄 두었던 "서버 전용 실행 파일을 따로 두는 길"이 필수 작업이 되었습니다. 지금 런타임 전체를 링크한 채 렌더러만
만들지 않는 길은 실행 파일이 그래픽 라이브러리에 계속 기대므로 택하지 않습니다.

**목표:** `HarukaServer` 실행 파일. 렌더러 · 창 · XR · UI · 입력 장치를 링크하지 않고, Linux x64 컨테이너에서 방 하나를 돌립니다. 개발 PC 에서 자동 시험을 돌릴 수 있게
Windows 에서도 같은 대상이 빌드됩니다.

**출발점:** E1b(2026-11-23)로 `HarukaSim`(장면 · 물리 · 소리 · 길 찾기)은 Vulkan · 창 · OpenXR 없이 링크됩니다. 서버가 씬을 읽고 게임 규칙을 돌리려면 그 위의 `components` ·
`assets` · `sceneio` · `runtime` 이 필요한데, 이들은 아직 렌더러를 끌고 옵니다([Engine_Structure_Design.md](Engine_Structure_Design.md) 15절의 17항목).

| 순서 | 할 일 | 지금 | 크기(추정) |
|---|---|---|---|
| S1 | **`HarukaSim` 의 Linux 빌드.** 루트 `CMakeLists.txt` 에 Linux 분기를 더하고 gcc 또는 clang 경고를 정리 | Linux 분기가 없습니다. 시뮬레이션 모듈에서 플랫폼을 가르는 파일은 일곱 개입니다(`core` 의 AppPaths · CrashHandler · SaveGame · TraceRecorder, `vfs/PakReader`, `audio` 의 AudioSystem · SteamAudioHrtf). Android 빌드가 이미 POSIX 길을 지나므로 조건식 정리가 대부분일 것으로 봅니다 | 중간 |
| S2 | **게임 규칙 컴포넌트를 서버가 링크할 수 있는 자리로.** 리그 이동 · 쥐기 판정 · 추적 자세 받기는 서버에 필요하고, 메시 컴포넌트는 서버에서 충돌 형상만 필요 | `components` 36개 가운데 11개가 렌더러 · XR · UI · 플랫폼 헤더를 include 합니다. 틱 입력(P3)으로 입력 싱글턴 의존이 사라지고, 쥔 자리 풀이를 클라이언트에 두면(D12) XR 모듈 의존이 사라집니다 | 큼 |
| S3 | **CPU 에셋 읽기를 GPU 올리기와 나누기.** 서버는 충돌 메시와 뼈대만 읽음 | `AssetManager` 가 렌더러를 받아 GPU 에 올립니다(`Engine.cpp` 526행) | 큼 |
| S4 | **시뮬레이션 루프를 `Engine` 에서 떼기.** 서버의 진입점이 틱 루프를 직접 돌리고, 화면 동기 대신 틱 간격을 맞추는 대기를 둠 | `Engine` 이 창 · 렌더러 · XR 을 함께 듭니다. D2 가 틱 루프를 만든 뒤에 떼는 것이 순서입니다 | 큼 |
| S5 | **`HarukaServer` 대상과 시험.** 서버 대상이 렌더러 · XR · UI · 플랫폼 · 입력 모듈을 include 하지 않는지 보는 아키텍처 규칙, 단독 링크 시험(`sim_link` 와 같은 방식), 새 `net` 모듈의 include 방향 규칙 | 없음 | 중간 |
| S6 | **운영에 필요한 것.** 서버 설정 파일, 표준 출력 로그, 종료 신호를 받으면 방 종료 절차(D9)를 밟기, 살아 있는지 확인하는 통로, Linux 의 크래시 기록, 컨테이너 이미지, EOS 의 Web API 를 부를 HTTPS 요청 기능(세션 등록 · 음성 토큰, D10 · D13) | 없음 | 중간 |

지킬 것과 알아 둘 것은 다음과 같습니다.

- **서버 설정 파일(사용자 답 30):** `engine.ini` 와 같은 `이름=값` 줄 형식의 서버용 ini 를 두고, 운영자가 고칠 값을 여기에 모읍니다. 이 문서에서 나온 항목은 다음과 같습니다.

  | 항목 | 기본값 | 나온 곳 |
  |---|---|---|
  | 방 인원 상한 | 8 | D9 |
  | 방 주인을 기다리는 시간 | 60초 | D9, 사용자 답 30 |
  | 주인 때문에 멈출 수 있는 횟수 · 멈춘 시간의 합 | 3회 · 180초(제안) | D9, 7-2 질문 40 |
  | 방을 나누는 방식 | 스토어별(나중에 "섞음"으로 바꾸면 크로스플레이) | D10 |
  | 지연 보정의 상한 셋(즉시 맞는 무기 · 휘두르기 · 던지기 앞당김) | 200 ms · 100 ms · 0 | D14 |
  | 자세 검사의 한도(머리 이동 속도 · 손 닿는 거리 · 머리와 캡슐의 거리 · 플레이 영역 상한) | 헤드셋 실험으로 정함 | D7 |
  | 시뮬레이션 틱 | 60 Hz(프로젝트 설정과 같아야 함) | D2 |

- **서버에 필요 없는 것은 서버 대상에 넣지 않습니다.** UI 패널 · 자막 · 렌더 추출 · 월드 UI 구동 · XR 세션 · 프레임 통계는 클라이언트 전용 라이브러리에 둡니다.
- **소리:** `HarukaSim` 에 소리 모듈이 들어 있습니다. 서버는 소리 모듈을 등록하지 않고 장치를 열지 않습니다.
- **프로세스 하나에 방 하나:** `PhysicsSystem` 이 Jolt 의 프로세스 전역 등록(`JPH::Factory::sInstance`, `PhysicsSystem.cpp` 231 ~ 232 · 287 ~ 288행)을 만들고 지우므로 한 프로세스에 물리 시스템
  둘을 띄우는 구성은 지금 안전하지 않습니다. D9 의 "방이 끝나면 프로세스를 끝냄"과 맞습니다.
- **`--headless` 는 서버가 아닙니다.** 렌더러를 그대로 만듭니다(C12). 서버 실행 파일이 생기기 전의 자동 시험에만 씁니다.
- **컴파일러가 셋입니다.** 서버는 gcc 또는 clang(Linux), PC 클라이언트는 MSVC, Quest 클라이언트는 NDK clang 입니다. 같은 소스라도 부동소수점 결과가 달라질 수 있고, 그 차이는
  예측이 어긋나는 원인이 됩니다. Jolt 결정론 옵션과 엔진 쪽 부동소수점 설정을 맞출지는 V3 실험으로 정합니다(D5).
- **S2 ~ S4 는 미룰수록 커집니다.** 게임 규칙 컴포넌트가 늘 때마다 렌더러와 섞일 수 있기 때문입니다. 3절 R9 를 지금부터 지키는 까닭입니다.

## 6. 단계 (큰 덩어리)

쇼케이스 게임에는 멀티를 넣지 않고 **즉시 투입할 수 있는 엔진 기능**으로 준비합니다(사용자 답 16). 기능을 끌고 갈 게임이 없으므로 단계마다의 기준을 `Projects/Samples` 의
멀티 샘플 씬과 자동 시험으로 삼고, 마지막에 프로젝트 템플릿이 서버 · 클라이언트 대상을 함께 만들게 합니다.

  중계는 단계에서 빠졌습니다.
